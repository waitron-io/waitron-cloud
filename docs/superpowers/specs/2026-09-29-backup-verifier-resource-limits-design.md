# Bound backup restore resources

D32 puts each restore in a fresh local Docker container. The trusted backup worker downloads and authenticates the object as before; it streams a bounded JSON header and encrypted artifact over stdin. Only the recovery key and snapshot identity cross this boundary. The verifier receives no database, provider, master-key or Docker authority.

Use an explicitly configured verifier image containing a tracked-only Waitron checkout with Linux dependencies and the existing restore adapter. Run it without network, capabilities, host mounts or writable image layers, as uid 1000 with no-new-privileges. A single size-limited tmpfs at /scratch holds input and restored files; /dev/shm is disabled. Set total memory and memory-plus-swap equally, a PID limit, CPU quota and existing process limits. Keep the Node permission policy. Default total memory is 1024 MiB and scratch 256 MiB, configurable within validated ceilings. A tmpfs uses that same memory budget.

The worker creates, attaches to, inspects and removes its uniquely named container. Cancellation kills/removes the container before returning. A 30-second deadline bounds execution; resource refusal is distinguished from that timeout by Docker OOM state or the process resource diagnostic. Startup removes only expired containers with its explicit owner label; live containers are never reclaimed. The image entrypoint also has its own deadline so worker death does not leave unrestricted execution. Cleanup failures fail closed.

Keep createWaitronVerifier as the process-only development adapter for existing proofs. The deployed worker requires the container image and owner configuration; it never silently falls back. The optional local backup profile grants Docker authority only to the trusted worker. No production deployment is authorised.

Evidence must include native Buffer allocation beyond the memory ceiling, many small files beyond total scratch, cancellation, interrupted-worker restart cleanup, simultaneous different venues, denied network/host writes and a later valid snapshot. Inspect actual Docker configuration and OOM state. Run the actual Waitron restore with a real locally generated encrypted archive in the image; synthetic restore modules are useful hostile fixtures but do not substitute for that proof.
