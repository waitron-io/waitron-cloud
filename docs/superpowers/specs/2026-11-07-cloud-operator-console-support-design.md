# D609: Support and the operator console

**Proposed; awaits owner review. Build nothing.**

Waitron runs on your venue computer (the box); Cloud provides managed services. You would choose each time: send a one-off copy of your box diagnostic, or approve time-limited support access to Cloud's stored venue diagnostic summary. Cloud staff can read submitted reports and, with your approval, that summary. They gain no repair or recovery powers. Their actions on customer data appear in your history. The design also lets a venue without a Cloud account send a bug report and diagnostic. The proposed receiver is Cloud in the country the sender chooses, without signup; Cloud's product owner must still confirm Cloud or a separate Waitron receiver. Ordinary problems remain self-service; this design adds no paid support, help desk or ticketing. Asking for help means submitting a problem report. The product owner still decides privacy, retention and the proposed one-hour access default.

## Choose each time

Download or send the copy from the app. Diagnostic sharing does not replace grant-based access, or vice versa. Revocation cannot recall a submitted copy; reading it needs no grant. Fresh/private inspection needs a grant; self-service needs none.

Waitron's [Report a problem plan](https://github.com/clintongormley/waitron/blob/147914ca764a66a6dfc7fbe8500ea66c53763100/docs/superpowers/plans/2026-10-22-a982-one-touch-problem-reports.md) owns capture, permitted fields, diagnostic size/event limits and preview. Its current scope is local capture, dialog and download. Cloud forwarding is neither built nor approved here. Separate Waitron task A1308 still holds changes to the `bug_reports` table. Do not duplicate the box design.

## Receive and read reports

Keep the existing authenticated customer staff-report route. **If Cloud is chosen for non-customers**, add a country-local intake without signup. It remains unbuilt and permits no reading. Apply Waitron's permitted fields, description preview/warning and size/event limits at both receivers; recheck them on the server and reject arbitrary attachments. The sender must choose the country before sending. Rate-limit each source and total country intake; cap simultaneous submissions and accepted storage; refuse before acceptance when full.

[The receiver](../../../packages/registration/src/box-error-reports.ts#L94) authenticates the registered box (installation), required by [report storage](../../../packages/registration/migrations/052_box_error_reports.sql#L1). If Cloud receives non-customer reports, add server-assigned country report IDs and storage/readers without customer associations. Never invent accounts/installations or trust submitted content or identity: neither proves ownership or customer-data links. Provide no public reading or identifier lookup.

Cloud staff independently authorised for support in that country read both report kinds in its console view. Reuse [the reader that groups reports](../../../packages/operations/src/staff-problem-reports.ts#L9), preserving empty logs and late/absent descriptions. Customer reports retain installation ID plus report ID as identity. Account/venue lookup by exact ID and browser routes are new work. Limit lists to the chosen country (the current reader returns up to 100 reports); every customer report disclosed enters that customer's history. Counts reveal no extra content. Receiving a report grants no private-inspection authority.

## Keep authority separate

The planned service separates country customer data from worldwide staff identity. The [country-account/operator separation](../plans/2026-10-22-cloud-global-country-split.md#4-separate-operator-authority) is prerequisite. Cloud staff need a separate worldwide identity; software in the country makes the final support-eligibility check. Support integration must first have its own scoped contract, permitted-action list and completed qualification checks. Your agreement cannot make staff eligible. Grant storage must use that country operator authorisation, without falling back to older account rules, matching emails or customer permissions. Enforcing one Cloud account owner per organisation is a prerequisite and remains unbuilt; today's store accepts any current owner. Preserve the linked plan's ownership-transfer revocations: end former-owner access and authority derived from that ownership. Handover remains separate, unbuilt work.

Customer records, report contents, contact, associations, grants and history stay in country. The worldwide service holds only records about staff and security, never report/contact data or identifiers. Browsers read countries directly and clear private results on country switching. The [Cloud action controller](../plans/2026-10-22-cloud-action-controller.md) remains planned. This design grants no repair, tax-related, server-activation, recovery or key-management powers, and no SSH access for running commands on a machine.

## Approve diagnostic access

The sole action, `venue.diagnostic.read`, uses [Download diagnostic's safe fields and rules for how recent data must be](../../../packages/account-http/src/diagnostics.ts#L12). Use the report's installation only while current, unrevoked and in the approved venue; otherwise refuse without substitution. Limit the grant to that venue, without a new installation field or querying the live box.

Record each display before showing the verified Cloud account owner's email. Deliver approval links manually: the [outbox](../../../packages/registration/src/email-outbox.ts#L64) and [templates](../../../packages/registration/src/account-mail.ts#L3) lack approval mail. This copies contact/link into the staff operator's mailbox; country/privacy handling remains unconfirmed. No production mail is authorised.

Without storing a request, the link carries an untrusted proposal: grant ID, operator ID, country, organisation, venue, exact action, reason and duration. It grants nothing. Country software resolves the operator name from its own qualified authorisation records, never the link, and rechecks inputs. As current sole Cloud account owner of the organisation, you authenticate again, review exact scope and expiry measured from approval, then approve or decline. Staff cannot self-approve. Only agreement calls adapted [grant approval](../../../packages/registration/src/support-grants.ts#L92). Reading its result by proposed ID repeats identical operator/scope checks.

Country support code must reject `venueId: null` (organisation-wide access), require fresh authentication and allow only that action; generic storage lacks these restrictions. Propose **one hour from approval**, with shorter choices and the [24-hour maximum](2026-10-22-cloud-data-protection-design.md#5-give-machines-scoped-keys-and-people-accountable-sessions). Changed scope/operator/action or extension needs fresh agreement. Declining creates no grant; the account website lists active grants and revocation controls. Staff then choose **Run diagnostic**.

Preserve [database transaction protection](../../temporary-support-grants.md#protect-database-work): database work commits together or rolls back together. Recheck current operator eligibility, owner authority, scope and time after waits and before disclosure. External revocation waits for running work, then blocks later work; expiry rolls back protected effects. Network calls and shell commands cannot be rolled back and stay outside. Disclosed data cannot be recalled.

## Record staff activity

Extend the [country activity record](../../security-audit.md) through a new database migration with predefined activity, actor and record types, authorised operator identity, installation-plus-report customer references and non-customer report subjects without an organisation. Current recording requires an organisation; adaptation is unbuilt. Customer reads, identifying lists, contact displays and refusals enter customer-visible history. Non-customer actions appear in the country's operator activity record and report view, without promising customer-account history.

Record who acted, fixed action/outcome, UTC time (the worldwide time standard), scope and report/grant reference, never contents, email values, request inputs, results or secrets. Reuse the planned action controller's records. Commit protected work/history together; recording failure denies disclosure. Record refusals separately after rollback; retries retain operation identity. Unbound failures (those without a verified association) record only operator/country/outcome/time worldwide, never entered IDs. Sending country security events to the worldwide service remains unresolved; browser self-report cannot replace it.

Keep [the command-line report reader](../../../packages/operations/src/staff-reports-cli.ts#L9), a tool run by typing commands. Replace its direct database reads with the same authenticated, recorded country route, without database credentials or general write permission. Routine reads cannot bypass history. Maintenance that reads no customer reports stays outside this report history.

Failure of the worldwide service or console stops staff access; country customer diagnostics, grant/revoke and history remain independent. Intake, console, grant screens, command-line integration and history extensions are unbuilt. Cross-repository reading covered only the pinned Report a problem plan; all source observations are reading only, with no runtime verification.
