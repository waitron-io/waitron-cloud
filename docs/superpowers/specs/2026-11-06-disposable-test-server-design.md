## Proposed choices and approval gates

- Use KVM/QEMU full virtual machines, or VMs, each with its own kernel, filesystem and Docker daemon. Allocate one fresh VM to one CI job or one bounded local command turn; destroy it afterwards. A container alone is insufficient isolation for hostile Docker work.
- Keep admission, GitHub credentials, lease records and the outage watchdog off the rented server. A lease is a time-limited, uniquely owned reservation for a slot. Use repository-level just-in-time, or JIT, runners: GitHub registers each to accept at most one job. Deregistration does not erase its VM.
- Choose visible failure and explicit hosted retry, rather than automatic fallback or a hosted dispatch gateway. Preserve native job identities and summaries. Do not introduce `pull_request_target`.
- Before activation, the owner sets approval for **ALL external contributors**, and you record current settings plus an unapproved returning-contributor refusal drill. This setting has **not** been verified. Workflow approval is not proof that candidate code is harmless. See [the exact repository policy choices](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository#controlling-changes-from-forks-to-workflows-in-public-repositories) and [GitHub's approval procedure](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/approve-runs-from-forks).
- The watcher must approve the public-repository residual risk below, the off-server broker location/operator and permissions, the machine-identity arrangement, outage bounds and benchmark gates. No new subscription, provisioning or spending follows from this proposal.

## Trust boundary, including what GitHub cannot promise

Your off-server controller runs only a reviewed, pinned main revision. It never imports candidate scripts, restores candidate artifacts as programs, runs package lifecycle hooks or executes candidate workflow expressions. Admission reconstructs the permitted job inventory using trusted-main policy and bounded data reads of immutable candidate Git objects. Treat candidate planner output as untrusted data; disagreement with the existing selection contract refuses enrollment and keeps the hosted path.

Allow only the configured Cloud numeric repository ID, workflow ID/path and reviewed workflow definition digest, event, head/tree, run ID, attempt, concrete matrix job ID/name and policy revision. Start with main pushes and explicitly approved same-repository PR heads. External PR execution requires the owner setting and per-head review gate above. Changes to workflow/control definitions stay hosted until reviewed main contains the new policy. Never authorize by actor name, a user-supplied label, webhook payload alone or candidate-provided environment variables.

Verify webhook signatures, deduplicate delivery IDs and independently query GitHub's current run/attempt/jobs. Poll as well as consuming events so missing webhooks cannot leave jobs unnoticed. Reject foreign repositories, unknown jobs, superseded heads, stale attempts, replayed reservations and unauthorized reruns before minting JIT configuration. An intentional rerun needs fresh admission, job IDs and leases. Give each expected job a distinct routing label derived unambiguously from repository/run/attempt/logical job/matrix row, and bind it in the ledger to the concrete GitHub job ID and returned runner ID. Prove label syntax and expression evaluation in the canary. Observe assignment using GitHub job records; a mismatch cancels the affected runs, retires that runner and quarantines its VM. It never becomes successful evidence for the intended job.

**Supported boundary:** the broker controls which requests create runners; repository registration limits which repository can schedule them; VM isolation protects the host and other slots. Repository-level JIT configuration has no documented job-ID binding. A malicious workflow in the same public repository can target any matching repository runner, including broad labels. Labels route work; they are not an authorization boundary. Comparing assignment after dispatch cannot guarantee that foreign job code has not already started. Do not describe a runner hook or a random label as a proven pre-execution security barrier.

You therefore accept a specific residual risk only after review: an approved malicious workflow may steal a slot, run once, consume its resources and read or exfiltrate that guest's transient credentials and inputs before detection. Approval mistakes, compromised maintainers, hypervisor escapes and broker compromise remain risks. The broker rejects foreign-job requests, but cannot enforce exact-only GitHub scheduling. If exact-only execution is required, this repository-runner design is unsuitable; keep those jobs hosted. [GitHub warns against public self-hosted runners and describes the limited one-job JIT guarantee](https://docs.github.com/en/actions/reference/security/secure-use#hardening-for-self-hosted-runners).

## Credentials and privilege separation

Use a narrowly installed GitHub App off-server, not a server PAT or reusable registration token. Split the registrar from the cancellation watchdog: the registrar needs repository Administration/write for JIT; the watchdog needs Actions/write to cancel runs. Give metadata/content/actions read only where needed. Keep App private keys, installation-token minting, webhook secrets and durable lease storage outside the rented server; do not send them to candidates. [The JIT API documents Administration/write and returns a runner ID plus encoded configuration](https://docs.github.com/en/rest/actions/self-hosted-runners#create-configuration-for-a-just-in-time-runner-for-a-repository).

The server's small privileged VM manager accepts only signed, expiring operations for its host generation and owned resource IDs. Its unprivileged transport cannot execute arbitrary shell, modify images or widen quotas. Candidate code lives only inside guests; the host never checks out a candidate. Guests cannot reach management networks, other guests, private services or metadata endpoints. Allow only required public download/GitHub traffic; test IPv4, IPv6 and DNS paths. Public egress still permits exfiltration of guest data.

Interpret **no lasting secret** literally: no persistent private service key, PAT, GitHub App key, package credential, registration token, runner credential, SSH host private key or provider credential on server storage, images, logs, swap, dumps or backups. Transient per-job JIT/session credentials may exist only within that job's disposable storage or memory. Destroy the encrypted guest disk's RAM-only key as well as the VM. Retain only redacted evidence off-server. Candidate code can see its own short-lived job credentials; destruction cannot recall data already exfiltrated.

**Unavoidable identity decision:** an authenticated controller must know which machine it is controlling. Proposed arrangement: you enroll a fresh RAM-only host key through an independently authenticated owner console session at boot, pin its public fingerprint off-server, and give enrollment a two-hour maximum. Disable disk swap, hibernation, core dumps and secret-bearing journaling; remove default persistent host keys from the approved image recipe. Reboot/expiry requires explicit re-enrollment and blocks new work. Public verification keys may persist; private keys may not. This sacrifices unattended reboot recovery. The console method, existing provider bootstrap credentials and whether this temporary machine identity satisfies your requirement need watcher/owner approval. Do not silently substitute persistent SSH, WireGuard or enrollment keys. If no trustworthy secret-free enrollment is available, stay hosted.

Every lease, including its cleanup allowance, must fit inside the remaining enrollment lifetime. Refuse a late start; expiry destroys outstanding guests and erases the temporary host key. A host-local absolute timer enforces those deadlines when off-server control is lost. Two-hour manual enrollment is an explicit operational cost, not a claim that unattended long-term identity has been solved.

Keep ordinary job permissions at `contents: read`, adding `packages: read` only for authenticated dependency consumers and `actions: read` only for evidence readers. No candidate `id-token: write`, repository administration, publishing credential or persistent SSH forwarding. Use checkout with `persist-credentials: false`. Local turns transfer an explicit snapshot, including intended uncommitted changes, but exclude `.git`, `.env*`, credentials, dependencies and local secrets; reject links/path escapes. Record tree/snapshot digest and command. Supply bounded package-read access through an off-server authenticated download service or fresh least-privilege job token, never `gh auth token` from your workstation. Qualify nested installs before choosing that adapter; inability to scope dependency access blocks local activation.

## Slots, ownership and bounded failure

The off-server ledger records repository/run/attempt/job or local lane/turn, head/snapshot, host generation, slot, monotonically increasing ownership generation, VM UUID, disk/network IDs, runner ID, policy/image digests, deadlines and cleanup state. Use atomic compare-and-set updates, so only the current generation can start, extend, cancel or release a lease. Duplicate deliveries return the recorded outcome, never another VM. An expired lease requests destruction; it never proves absence. Do not copy the helper's age-based lock stealing.

Keep separate guest networks, Docker sockets, writable disks, package stores, ports and temporary directories. Never expose the host Docker socket, host bind mounts or shared writable caches. Build immutable base images from reviewed inputs; each VM receives a fresh private copy. Any restored dependency cache is copied into the guest, treated as untrusted and isolated by trust/head policy; candidates cannot publish a shared trusted cache. No candidate output becomes a base image. A cleanup refusal quarantines the owned slot and blocks its reuse until absence is verified.

Use these **proposed** limits; they are acceptance targets, not measured behavior:

| Stage | Bound and observable failure |
| --- | --- |
| Local admission | Reply within 10 seconds; busy/down returns 75 immediately, without waiting behind CI. |
| CI queue, including capacity wait and boot | At most 15 minutes from GitHub job creation; boot at most 120 seconds and online-to-start at most 60 seconds, all inside that queue budget. Expiry cancels the exact run. |
| Execution | Preserve each existing CI job timeout and child deadline. Local command execution at most 55 minutes; no keep-open service turn. |
| Health/outage | Heartbeat every 15 seconds; 60 seconds without health stops admission and requests exact-run cancellation. Poll queued runs/jobs every 15 seconds, even when no VM exists. |
| Cleanup | Terminate within 30 seconds, force-stop only the owned VM, then verify disk/key/network/runner removal within 120 seconds total. Unknown outcome quarantines, never frees capacity. |
| GitHub cancellation | Request within 15 seconds of detected expiry/outage; allow 30 seconds, then force-cancel an unresponsive run. Read back terminal state within 120 seconds of detection. API failure alerts and blocks admission; it cannot guarantee GitHub's terminal-state deadline during a GitHub outage. |

Use two independently supervised off-server watchdogs. Proposed placement is the existing Mac for primary admission and the existing test box for a cancellation-only standby, subject to watcher approval before installing either service. This adds no rented machine or subscription. Each supervisor restarts its own process within 30 seconds; each watchdog polls GitHub and the other watchdog every 15 seconds. After 60 seconds without primary health, the standby stops server admission and cancels affected current runs under the cancellation bounds above. It also discovers queued jobs with no lease, including jobs created after primary-host loss. Do not route required work to the server until both watchdogs pass readiness checks.

Before registering a runner, durably mirror its exact identity, immutable deadlines and cancellation intent to the standby and require acknowledgement. The standby retains trusted policy and an independent Actions/write credential off the rented server; it neither registers runners nor executes candidate code. Loss of the standby stops registration, and the primary cancels outstanding server work rather than continuing without redundancy. Exercise process death and complete loss of either management host, including loss before any VM exists. Simultaneous loss of both management hosts, or a GitHub API outage, cannot promise a terminal-state deadline; record this limit and keep admission closed on recovery. Normal and force cancellation use [GitHub's run-ID APIs](https://docs.github.com/en/rest/actions/workflow-runs#cancel-a-workflow-run). Recheck the current attempt before cancelling; that API addresses a run, not an individual attempt. Observing a newer attempt invalidates the old cancellation intent and requires independent reconciliation. There is no documented atomic attempt-conditional cancellation: a manual rerun between read and cancel remains a race. Require operators to serialize reruns through the controller after old cancellation retires; demonstrate refusal of stale intents. Uncoordinated manual reruns are outside the supported operating contract and may themselves be cancelled. Watcher acceptance of that API limit is required; do not claim a read eliminates it.

If the server disappears, a watchdog cancels the affected native workflow run. Cancellation can leave required work or `summary` cancelled or unexecuted, rather than manufacturing a failed summary. Cloud has no GitHub-enforced branch protection. Its driver must enumerate every actual current-head job and refuse landing for cancelled, missing, queued, running or failed required work, while retaining the shared landing lock. Rehearse that real driver refusal with a cancelled canary; a dashboard-only alarm is insufficient. No branch-protection change, hosted gateway or extra required job is proposed. [GitHub can queue an unmatched runner job for 24 hours](https://docs.github.com/en/actions/reference/runners/self-hosted-runners); `timeout-minutes` does not solve that queue. GitHub does not automatically switch it to hosted capacity.

Use one shared local-plus-CI budget. Serve runnable requests round-robin across local lanes and CI runs, one slot per owner before granting extra slots. Local callers retry after 75 without holding a queue place. When measured capacity reaches two, reserve one opportunity for waiting CI and one for local turns, lending idle capacity until the next release. Bound pending requests to 32 and CI waiting to 15 minutes; reject excess requests visibly. An unapproved fork awaiting human review is not a resource lease; admit only after approval. Never delete shared machine resources or run any form of Docker prune.

## Measure before sizing or expanding

[GitHub's public standard Ubuntu reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners#standard-github-hosted-runners-for-public-repositories) lists 4 CPUs, 16 GB RAM and 14 GB SSD. Sixteen physical cores do not equal sixteen such runners. Verify delivered topology, virtualization, usable disk after the chosen layout and sustained thermals first; the two drive labels do not establish usable capacity.

Proposed initial benchmark profile: one VM, 4 vCPUs, CPU quota 4 CPU-seconds/second, 16 GiB RAM and 64 GiB maximum private disk. Reserve at least four physical cores including their sibling threads, 16 GiB host RAM and 20% usable disk for management/image/cleanup headroom. Pin guests away from reserved cores, do not count SMT threads as extra physical cores, and never overcommit RAM. Admit only if combined local+CI CPU quotas, memory, maximum disk allocations, images and quarantined resources fit the measured budget. Disk and I/O pressure can reduce capacity before CPU does.

Compare the exact same selected job, head/tree, commands, image/tool/dependency versions and test inventory on hosted and rented paths. Run at least three cold and three warm-cache trials at one slot, then two and three concurrent slots, including mixed local/CI work and a bulky Docker/browser workload. Warm means a fresh guest with an isolated copy of a verified dependency cache, never a reused job VM. Record wall/queue/boot/cleanup times, CPU time/throttling, peak resident memory (RSS), host available memory, I/O latency/throughput/pressure, disk high-water/free space, network bytes/download failures, test/pass/skip counts and every effective cap.

Gate each increase on zero missing assertions or additional skips, no changed child deadlines/concurrency/workload, no resource collisions, no host reserve breach or out-of-memory kill, cleanup <=120 seconds and queue <=15 minutes. Proposed performance gate: median execution no slower than hosted and no trial slower than 1.25 times its comparable hosted maximum or the existing job deadline. Keep failures in the sample. Also measure the complete selected/full/nightly queue with proposed caps before broad rollout: short individual jobs do not establish sufficient throughput for all partitions. If a gate fails, retain the lower count or hosted execution; do not loosen tests to fit. Production slot count remains unknown until measured and watcher-approved.
