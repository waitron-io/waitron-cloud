# Test Cloud with free and pretend-paid organisations

You need a Cloud destination you can connect a disposable Waitron venue to, without billing infrastructure or disturbing the test box's existing venue. D79 adds a small organisation plan and a separate LAN deployment. A plan permits a service; provisioning, consent, credentials and release gates still decide whether it works.

This is a proposed implementation design, not a deployment receipt. The documentation PR contains this design, its [implementation plan](../plans/2026-10-17-test-cloud-free-paid.md) and the backlog update. Implementation is authorised within the test-only scope below. Land the reviewed documents before product changes.

## The smallest plan boundary

Add `organisations.service_plan`, constrained to `free | paid`, default `free`, and `service_plan_revision`, initially zero. There are no trials, subscriptions, payments, customer plan endpoints or automatic provider provisioning. The new metadata defaults to free, including on existing rows, but changes no existing permission by itself. Enforcement is opt-in to the isolated test deployment through `CLOUD_TEST_SERVICE_PLANS=1`; ordinary deployments default to `0` and retain their current behaviour. Reject other flag values at startup. Pass the validated mode explicitly to the API, trusted stores and workers; do not read ambient environment inside policy helpers. In enabled mode reject non-test venues regardless of the stored plan. Production plan enforcement and customer cancellation/retention policy remain outside D79.

Keep the deployed flag off until all configuration, backup, direct-storage and gateway boundaries are implemented and the complete integration proof passes. Intermediate PRs add dormant capabilities; none activates a partially enforced plan. The CLI also requires this explicit test mode. Tests opt in only when exercising the new policy; keep ordinary deployment assertions unchanged.

Provide an internal `OrganisationPlanStore` and a database-backed operator CLI:

```sh
node packages/registration/src/organisation-plan-cli.ts show --organisation <uuid>
node packages/registration/src/organisation-plan-cli.ts set --organisation <uuid> --plan paid
node packages/registration/src/organisation-plan-cli.ts set --organisation <uuid> --plan free
```

These are proposed commands. They return only `{organisationId, plan, revision, changed}`; `show` has `changed: false`. Setting the same value is a no-op. Unknown organisations, invalid arguments, database failure and incompatible migrations fail without changing anything or printing credentials. Run the CLI inside the Cloud project so the database URL comes from its private volume. Later billing may reuse the setter after a separately reviewed production policy.

Do not include fiscal allocation in the service type or paid policy. Do not alter fiscal records, schema, continuity, signatures or expected golden results. Keep the runtime's independent fiscal configuration absent. A paid organisation must still get the existing unavailable refusal on fiscal writes.

### Configuration, races and downgrades

In the enabled test mode, use one organisation policy helper at trusted service entry points; derive the organisation through the stored venue/installation, never the request. Permission failures use existing machine `403 permission_denied` and existing account permission errors. An unavailable policy database defers/fails closed; it never implies paid.

Plan changes and service checks must share a documented lock order. Authenticate accounts and lock membership as required first; where both are needed, lock organisation policy before installations, then existing service/location locks. Recheck the original binding under those locks. The setter locks affected installations in stable UUID order, advances their configuration revisions once per actual plan change, and on downgrade clears the three paid service configurations/states to `unconfigured`. It does not revoke the installation or translation entry. Trace and correct reverse lock acquisition in every new policy reader; concurrent pairing, replacement and operator work must not deadlock or escape the organisation update.

Every fresh or replayed `renew`, `configuration`, `report`, account installation list and trusted configure result must apply current permission before returning paid configuration. A cached operation reply is not durable permission to reissue secrets. Preserve existing signed request bodies, lease durations, service names and the three/four-service negotiation. Do not add a plan field to the Waitron wire. On upgrading, explicit provisioning must refresh the cleared setup before it can work again.

The current idempotent provision paths return an existing location/placement without restoring cleared setup (`packages/backups/src/catalogue.ts:223`, `packages/remote-access/src/placement.ts:71`), and streams bind to a configuration revision (`packages/backups/src/managed-streams.ts:310`). Re-enable these through explicit trusted reprovisioning with a fresh writer and current revisions; merely setting paid again must not revive stale authority or leave the service permanently unusable. Preserve objects, recovery keys and existing recovery operations while refreshing the current binding.

Enforce paid permission before provisioning, credentials or keys escape, and again after each external wait. Cover snapshot reserve/publish, catalogue provision/key rotation, stream configure/observe, recovery approval/target access and replacement completion. Free owners may inspect already stored backup metadata/status and close a recovery, but cannot obtain new data/key grants or activate a replacement. Preserve stored objects and key versions on downgrade. For this bounded test deployment only, retain the last verified snapshot and pause retained-snapshot expiry while free; abandoned staging cleanup remains safe. This test-data preservation default does not change ordinary deployment retention or establish a customer cancellation/deletion policy. Verification may finish previously admitted snapshots; it cannot create new customer grants.

For remote access, check placement/moves/hostname changes, certificate submit/status/authorization/publication and both active and staged manifest routes. The reconciler must derive the same filtered desired set; downgrade removes routes, peers and unstarted certificate work. Already signed authority expires within its existing ten-minute ceiling if publishing stops. Report observed withdrawal separately from the committed plan change.

Direct storage is a second permission boundary. The snapshot STS adapter requests 900 seconds and validates returned expiry at no later than approximately 901 seconds (`packages/backups/src/storage.ts:136–148`). Those source checks do not prove that storage refuses an expired credential. Measure a real post-expiry request before claiming a bound on residual access. Managed stream fixture credentials currently have no expiry (`scripts/backup-storage-fixture.mjs:320`); API checks alone cannot stop their writer. The test deployment must persist per-venue identities privately and remove/reload the downgraded venue's writer identity, retaining Cloud's recovery reader separately. Prove old credentials fail against storage, including restart recovery of a pending withdrawal. Re-upgrade uses a fresh writer. Do not report withdrawal complete while old access still works; record the remaining bounded STS exposure honestly. A provider requiring a new Waitron credential-renewal action needs an owner wire decision, not an invented protocol.

Free services keep their current independent gates. Relay approval/admission and worker handoff remain bound to grant revision, live ownership, origin, expiry, allowance and kill switch. A paid toggle neither creates nor revokes an email grant. Translation submit retry precedence, signed ownership-first reads, status/collect/release after lost consent/readiness, worker consent and spending checks stay unchanged. Keep archived prompts, trial data and recorded prices unchanged.

## LAN deployment

Use Compose project **`waitron-cloud-test`** on `clinton@waitron.local` (`192.168.10.10`). Choose canonical portal origin **`https://waitron.local:3000`**. This is a driver default within the authorised LAN scope. Verify resolution to the expected LAN address on clients; use a test-client hosts entry if mDNS is unavailable. Never publish DNS or add internet/router forwarding.

Terminate TLS in a Cloud-owned proxy on `192.168.10.10:3000`, forwarding only on the private Compose network to the account HTTP listener. Preserve the exact Host and canonical Origin; strip caller forwarding headers and trust only the explicitly configured proxy peer. Do not publish the account backend. Propagate the same origin to account mail, pairing/lease signing, health checks and portal links. The existing local mailer rejects non-loopback origins, and the production SMTP mailer rejects `.local` (`packages/registration/src/local-mailer.ts:14–17`, `smtp-mailer.ts:28–30`). Add an explicit test-only capture mailer selected only by the test runtime. It renders links with the validated canonical HTTPS origin, sends only to this project's fixed Mailpit loopback listener in the shared mail network namespace, and accepts no caller-supplied SMTP destination. Keep both existing mailer validators unchanged. Prove actual signup mail and its link over LAN HTTPS, not just environment propagation. Ordinary local Compose remains `http://localhost:3000` on loopback. Leave production origin, Host, CSRF, cookie, passkey, redirect and request-limit guards intact.

Bootstrap a private local CA and leaf certificate for `waitron.local` / `192.168.10.10` inside the project configuration volume. Distribute **public certificates only** to the disposable Mac browser profile and its Node clients. Use a scoped CA bundle, such as `NODE_EXTRA_CA_CERTS`, with normal verification; no insecure TLS switches or skipped certificate errors. The owner's browser may need to trust that public CA before using passkeys; a certificate-warning bypass is not equivalent. CA/leaf renewal preserves the project identity and does not copy private keys to host files.

Keep PostgreSQL 55432 and Mailpit 1125/8125 on loopback. Read Mailpit through an owned SSH tunnel. Publish storage on `192.168.10.10:8333` only once scoped authority works; advertise `https://waitron.local:8333`, with a matching trusted certificate and resolution from both Cloud containers and Mac clients. Do not return `https://storage:8333` to a LAN client. Keep gateway 8443/UDP 51820 loopback until its explicit LAN proof is ready, then bind only the LAN address. No use of Waitron's 80/443/9110/1025/8025.

Use a test deployment override with Compose `!override` port replacement; require Compose **2.24.4 or later** and verify the rendered bindings. Its generated inputs, relay fixtures, gateway inputs, storage identity map and secrets all live in project volumes with private permissions. No remote source checkout, secret bind mounts or remote builds. Build Cloud and the pinned Waitron verifier for **linux/amd64** on the Mac with the existing BuildKit token secret; stream images through SSH into Docker. Transfer only reviewed non-secret deployment files and image digests. Never put `NODE_AUTH_TOKEN` or generated secrets in host files, logs, image layers, shell tracing or receipts.

The base gateway manifest deliberately exports no routes, and the normal backup runtime does not provision a client-facing storage service. Add explicit test-only adapters using genuine existing local proof components: scoped SeaweedFS STS and persistent managed identities, the existing remote store/reconciler, locally issued certificates and real WireGuard/HAProxy. Do not hand a venue the storage admin key or pretend an empty gateway is remote access. Keep the default local stack and production provider gates unchanged.

Outside-home remote access remains unavailable without a separately approved real domain, trusted certificates and deployment. A local CA does not make the Cloud public. Address providers stay disabled; translation stays off until pinned joint paging proof and owner Tasks 22–24 after **2026-11-02**. Relay remains opt-in local proof with Mailpit; private-LAN origin verification is fixture-bound to the disposable venue and test CA, never an always-success verifier.

### Resource and rollback defaults

These are conservative **driver defaults**, not previously promised Waitron requirements: start only with at least 4,096 MiB available RAM and 20 GiB free disk; preserve at least 2,048 MiB available and 15 GiB free. Bound Cloud's steady containers to 2,048 MiB aggregate plus at most one 1,024 MiB verifier (256 MiB scratch counts inside that limit), including any owned verifier child. Limit fixture storage to 1 GiB and rotate container logs. Reconcile these budgets against a real idle/active measurement before increasing load.

Record the IDs and labels of every Cloud container/network/volume/image/fixture you create. Sample memory, disk, Cloud usage and the three quarantined Waitron containers every five seconds during startup and proof, and for a sixty-second settled window. Stop owned Cloud work on any OOM, Waitron health regression or three consecutive below-floor samples; collect redacted evidence. Never stop or restart Waitron to make room.

For rollback, stop only recorded Cloud IDs and preserve volumes. A schema change requires a private volume-to-volume backup before migration; restore the matching database/config/storage set with its old image if needed. Do not run an old binary on a newer schema. Do not use global prune, name-based process kills or broad `--remove-orphans`; destructive reset is not the rollback. The trusted verifier controller has Docker-socket authority, so review its exact owner labels/child IDs before enabling it on this shared host; untrusted verifiers retain no network, no socket and no host mounts.

## Proof and operator handoff

Create two distinct test organisations through normal signup/verification, captured only by Cloud Mailpit; leave one free and set the other paid with the new CLI. Use distinct disposable Mac Waitron venues/state directories to pair them. Never re-pair the same venue into a different organisation to fake the comparison, and never start, upgrade, reseed or connect the quarantined box venue. Read Waitron main only; install a pinned genuine client/fixture in this lane's scratch for proofs. Do not edit another lane's checkout.

Prove a working free service against each organisation: Cloud signup/recovery mail in Mailpit, plus the genuine Waitron pairing/lease/configuration exchange. Separately exercise local relay grants/admission/worker capture and translation fake-provider consent/submit/collect/release; label these Cloud fixture proofs, not an available Waitron relay or production translation journey. The deployed translation endpoints must still return `503 temporarily_unavailable`.

Try signed snapshot reserve against both: free must return `403 permission_denied` with no grant/key; paid must upload a real disposable Waitron archive, publish and verify it, then recover it through existing restore consumers without trading activation. Exercise paid stream capture/recovery separately, including snapshot recovery with that stream absent. Prove free remote provisioning/certificate refusal and paid LAN staff/public route isolation; include downgrade with cached replies, blocked provider waits, existing stream credentials, staged routes and reconciler restart. Removing each critical guard in a disposable installed copy must make its named behavioural assertion fail.

The operator runbook added during implementation must show project-scoped commands, public-CA setup, normal Settings → Cloud services pairing, plan show/set, service matrix, health versus integration checks, Mailpit access, measured capacity, safe restart/upgrade/rollback and exact redacted refused outputs. Explain why the box venue remains untouched. Include Cloud/Waitron/image revisions and distinguish planned defaults, observed results and unavailable dependencies.

No new wire decision is required by this design. **Current Waitron main cannot qualify paged Translate all and cannot originate a Cloud-relayed account message.** D79 must report those unavailable, retain its release gates, and coordinate the separately owned client work through the parent. If an actual paid-service proof cannot use the existing signed contract, stop that slice and give the parent the exact incompatible request/response and one owner decision; do not broaden D79 silently.
