# D621 existing-session failure diagnostic

When a measured machine stop fails an existing account session check, the rehearsal’s stderr must show the HTTP status or transport error, elapsed milliseconds and the answering account proxy node when a response identifies it. This gives the operator a way to investigate the Stockholm failure. The first free trace reached the account through the surviving proxy, but the paid run reported only `p1.session_after_recovery` before teardown.

Reuse the session request and response handlers in `scripts/test-cloud-integration.mjs`, the five-second observer limit in `scripts/p1-observer.mjs`, and the test-only account proxy in `scripts/kubernetes-services.mjs`. The prior disposable Kind trace showed that HAProxy’s response hook can identify the node even when the proxy generates its own HTTP error. Keep the status assertion, cancellation and deadlines. Paid qualification, production routing, other probes and the cause of the Stockholm failure remain outside this change.

1. Write failing coverage for forced HTTP 503 with a node, a reset before headers with no node, and a successful session check with no diagnostic. Use the existing client test file `scripts/test-cloud-integration.test.mjs`. Drive the session adapter with a loopback HTTP exchange, then assert that stderr retains the diagnostic when the check rejects. Include a response body and error message with synthetic private canaries and assert the trace excludes both. Use the existing post-recovery deadline case in `scripts/p1-observer.test.mjs` to check the time limit stays in force.
2. In the measured-stop session request only, capture status and node as soon as headers arrive, before decoding the body. On a non-200 result or a rejected request, emit one structured stderr line with those fields, elapsed time from a monotonic clock and a bounded error code or class if the request failed. A response before a reset can still identify the node. A reset before headers leaves the node unknown. Keep using the existing status assertion and error handling.
3. In `scripts/kubernetes-services.mjs` and `deploy/kubernetes/services.mjs`, reuse the account proxy sidecar in the outside baseline and the Kubernetes node field already used for mail. Put the node response header on the session path only, including proxy-generated replies. Extend `scripts/kubernetes-services.test.mjs` and `deploy/kubernetes/services.test.mjs` at the configuration boundary. Exercise the rendered proxy with a local refused account request to show the node survives its HTTP failure.
4. Run the four named test files with `node --test` and the focused proxy check. Record the forced-failure output and update D621 in `docs/backlog.md` with what it proves and what remains open.

Expected size is about 45 production lines added and 8 removed, 85 test lines added and no assertions removed, plus the backlog update. All data is synthetic and the proof uses loopback. Any Stockholm run needs separate approval.
