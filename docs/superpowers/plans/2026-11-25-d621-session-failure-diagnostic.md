# D621 existing-session failure diagnostic

When an existing account session check fails during an individual measured stop, the rehearsal’s stderr records the HTTP status or transport error, elapsed milliseconds and the answering account proxy node when known. The 25 November Stockholm run stopped at `p1.session_after_recovery` during the second leg. At that run’s revision (`ae24c2efc5f5`), [the observer](../../../scripts/p1-observer.mjs) could keep the underlying error as its cause, while [the launcher](../../../scripts/amazon-run.mjs) printed only the outer message. The cause and paid qualification remain open.

1. In [the existing client tests](../../../scripts/test-cloud-integration.test.mjs), first drive the real session request and `observeP1` in a child process over loopback TLS. A successful session check after the stop must precede a forced HTML HTTP 503, a connection reset before response headers, or a silent connection that reaches the five-second limit. Assert the child exits 1 with the observer’s session failure and a single matching diagnostic. Check status and node on the 503, reset code and unknown node before headers, and a timeout at the existing limit. Earlier successful session checks stay quiet. Check that the failed output excludes synthetic private values in the response, cookie and error messages.
2. In [the test client](../../../scripts/test-cloud-integration.mjs), share the existing HTTPS exchange by moving it into `requestIntegrationApi(options, body, download, onHeaders)`. Take status and node at headers, before JSON decoding. Wrap the session probe only in the options passed to `stopServices`. Label early caller cancellation separately from the five-second transport deadline. The full restart and the legacy single-worker observer keep their existing probes.

Replies from an earlier hop or a connection that never sends headers have unknown nodes.
