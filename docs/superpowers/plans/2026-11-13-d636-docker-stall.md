# D636: identify the fresh-runner Docker stall

**Ask and finish line.** The watcher assigned the recurring first PostgreSQL image-inspection stall (Lane G queue, 13 November 2026 19:04). D636 requires a cause-supported repair, unchanged 120-second acquisition limit and assertions, then a manually started successful full nightly on main. This proposed prerequisite supplies missing failure evidence only; watcher clearance is required and D636 stays open.

**Evidence.** Runs [41859910075](https://github.com/waitron-io/waitron-cloud/actions/runs/41859910075), [42094443206](https://github.com/waitron-io/waitron-cloud/actions/runs/42094443206) and [43413690187](https://github.com/waitron-io/waitron-cloud/actions/runs/43413690187) stop before their first database, on three Ubuntu 26.04 images. The first has no browser install and inspection starts seven minutes after its first log. Only the latest records uptime: 250.66 seconds after inspection times out (120,091 ms), low load, about 15.8 GB free and a separate one-second Docker-client timeout. Startup delay and a blocked daemon remain hypotheses; no retained service state or journal establishes either.

**First cut.** Extend only the existing failure reporter in `scripts/docker-stall-diagnostics.mjs`, gated by `GITHUB_ACTIONS=true`, `RUNNER_ENVIRONMENT=github-hosted` and Linux. After the existing timeout/probe: one `systemctl show` reads Docker/containerd/socket `ActiveState`, `SubState`, `Result`, `MainPID`, `NRestarts`, `ExecMainStartTimestampMonotonic`, `ActiveEnterTimestampMonotonic`; one curl requests `/_ping` through `/var/run/docker.sock`; one `sudo -n journalctl` reads this boot's Docker startup events. Keep only fixed state values, numeric fields, socket outcome and monotonic timestamps/counts of “Daemon has completed initialization” and “API listen on”; discard raw output/errors. Each of these three commands has a one-second forced-kill limit and bounded output, at most three extra seconds beyond today's one-second probe. Report journal unavailability rather than escalating permissions. Boot uptime and systemd/journal monotonic times are separate observations. No retry, wait, service mutation, workflow or runner-version change.

**Tests and size.** Reuse `scripts/ci-test-postgres.test.mjs` and its child-process preload. Explicitly clear runner markers in existing cases; new hosted-Linux cases control platform and all three external commands in that preload. Watch new cases fail first: starting service versus active service/socket timeout; fixed journal-event extraction; missing/hung/malformed/private replies; unchanged original failure and no extra probes on ordinary launches. Run that file and root-ownership controls. Update `docs/backlog/verifier-build.md` and `docs/backlog.md` without closing the repair. Expected production +60/-5, tests +90/-0, docs +25/-10, support 0. After this lands, manually run the nightly to check for regressions, never as proof of a stall repair. Actual stall evidence must precede the repair plan, its Claude read and watcher clearance.
