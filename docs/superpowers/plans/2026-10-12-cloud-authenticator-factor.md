# Cloud authenticator factor implementation plan

> **For the driver:** Execute inline with `superpowers:executing-plans`. Read `superpowers:test-driven-development` before writing code. Land the approved design and checked plan first; deliver one cohesive implementation PR. No additional design confirmation is required.

**Goal:** Add optional authenticator-app protection to Cloud password login and account controls.

**Architecture:** Identity owns cryptography and password authority; registration owns transactional factor state and challenges. HTTP preserves existing protections; the portal keeps temporary proof and secrets in tab memory.

**Stack:** Node 26+, TypeScript, PostgreSQL 18, pnpm 9.15.0, Hono, Lit, Chromium.

**Spec:** [Approved design](../specs/2026-10-12-cloud-authenticator-factor-design.md).

## Constraints and evidence

Reset preserves the factor and unused codes, ends sessions and invalidates pending factor challenges. Successful activation/replacement/removal/regeneration ends **all** sessions atomically. Passkey login remains independent; a passkey/session plus recovered password cannot alone manage an active factor. No support bypass, mandatory MFA or Waitron changes.

These are code readings, not runtime proof. Cloud read at `2994da1b9bdaf73cab0063c3e28582663e782e6d`; the design's earlier Cloud pin is not this checkout. Existing paths below were inspected; additions are explicitly marked **new**.

Consumer/lock receipts:

- `packages/identity/src/sessions.ts:32–77`: `login` derives before account SHARE then credential SHARE, rechecks the password hash and calls `createSession`. `requireCurrentPassword` has equivalent rechecks. `createSession` is also called by `packages/registration/src/passkeys.ts:179`; keep this trusted primitive independent of password MFA. - `sessions.ts:80–153`: resolution locks account SHARE then actor session UPDATE and samples `clock_timestamp()` after waiting. Logout updates its session; HTTP resolves first (`packages/account-http/src/app.ts:171`). Revocation takes the account advisory lock **before** resolution, then target session and actor recheck. Never take that advisory lock from inside a factor operation holding the account row.
- `packages/registration/src/password-recovery.ts:60–84`: screening/derivation, account UPDATE, credential UPDATE, reset request UPDATE, session revocation, notification, terminal expiry-checked consumption. Keep its terminal check and outbox atomicity. `email-outbox.ts:205–210` also checks reset password fingerprints. `history-cleanup.ts:99–114` deletes eligible sessions and protects WebAuthn references; factor pending-session references need equivalent protection.
- `packages/registration/src/passkeys.ts:70–137,144–201`: management resolves then checks password; authentication locks account then passkey and creates its session independently. `packages/account-http/src/app.ts:146–153` writes login cookies; `apps/portal/src/api.ts:32` and `app.ts:244` assume full login success. All three must branch explicitly.

Proposed factor lock order: nonlocking account discovery and password derivation; account **UPDATE before any session/credential child lock**; credentials; actor session; factor state; challenges/proofs; remaining sessions in stable order. Reset already starts with account UPDATE. This serializes absent-factor enrolment too, avoids SHARE-to-UPDATE upgrades, and waits for existing SHARE-based consumers. Revalidate discovery, password fingerprint, factor version, session/CSRF and database wall time after expensive work and every contended stage. Before effects, acquire remaining required locks and check again; after potentially blocking writes, apply terminal deadline checks, rolling back all successful proof/change effects if expired.

## Interfaces and proposals

All names here are **proposed**, except existing functions named in the receipts. Adopt the spec's six digits/30 seconds/adjacent steps, issuer `Waitron Cloud`, AES-256-GCM, ten random 128-bit recovery codes, and five-minute login/pending lifetimes. Inspect installed upstream `otplib@13.5.0` and `qrcode@1.5.4` as candidates; pin actual dependencies at implementation. No production rate, attempt-budget or retention values are selected. Inject validated budgets/rules; absent policy disables new factor operations, never existing no-factor login or passkeys. Tests use explicit small budgets.

Proposed types: `FactorProof = {kind:'totp'|'recovery'; code:string}`; `Authority = {token:string; csrfToken:string; password:string; proof?:FactorProof}`; `FactorKeys = {activeKeyId:string; keys:Readonly<Record<string,string>>}`; `FactorBinding = {accountId:string; version:number; purpose:'active'|'pending'; pendingId?:string}`. `FactorPolicy` supplies `loginLifetimeMs`, `pendingLifetimeMs`, `challengeAttempts`, `enrolmentAttempts` and `{limit:number,windowSeconds:number}` rules named `loginAccount`, `completeIp`, `completeAccount`, `completeChallenge`, `manageIp`, `manageAccount`. Parse explicit `CLOUD_FACTOR_POLICY`; validate exact keys/positive bounds without production defaults.

Proposed key outage behaviour: status and existing live-session account access remain available; passkey sign-in remains available. Missing/malformed keys or unreadable active ciphertext refuse both factor password-completion methods and management; never treat unreadability as “no factor.” No-factor password login remains available. Loading bad factor configuration must not prevent the account server from offering these independent paths.

Review focus, covered in tasks below: expiry behind locks; reset during password derivation; activation-code replay; regeneration accidentally clearing replay state; lost successful replies and stale browser responses.

## 2. Password challenges without a bypass

**Modify:** `packages/identity/src/sessions.ts`, `packages/identity/src/index.ts`, `packages/registration/src/index.ts`, `packages/registration/test/identity.test.ts`.
**New:** `packages/registration/src/password-login.ts`, `packages/registration/test/password-login.test.ts`.

Extract proposed `requirePasswordAuthority(client:PoolClient,who:{email:string}|{accountId:string},password:string,lock:'share'|'update'):Promise<{accountId:string;passwordFingerprint:string}>`. Preserve one dummy derivation and generic refusal; recheck the exact snapshot after locking. Existing `login` keeps its no-factor `SessionCredentials` signature but refuses active factors, preventing scripts/direct callers bypassing MFA. Existing `requireCurrentPassword` delegates without weakening assertions.

Produce `PasswordLoginStore(pool,keys,policy)` with `start({email,password})` returning `{kind:'session',credentials:SessionCredentials}` or `{kind:'factor',challengeToken:string,expiresAt:string}`; `complete(challengeToken:string,proof:FactorProof):Promise<SessionCredentials>`. Completion locks/rechecks account, credential, factor and challenge before atomic proof/challenge consumption and session creation. Accepted TOTP records every match and rejects a live repeated code; recovery updates only an unused matching account/version code.

Return an internal refusal result from `transaction`, commit spent attempts, then throw the public error **outside** it (`transaction.ts:19` rolls back thrown errors). Place an effect savepoint after spending attempts; late expected refusal rolls back proof/session/change effects to that savepoint, preserving the budget. Unexpected database failures roll back the transaction. Never return an account ID with a challenge.

## 3. Management, reset and lifecycle races

**Modify:** `packages/registration/src/index.ts`, `packages/registration/src/password-recovery.ts`, `packages/registration/src/history-cleanup.ts`, `packages/registration/test/password-recovery.test.ts`, `packages/registration/test/passkeys.test.ts`, `packages/registration/test/history-cleanup.test.ts`.

Produce `AuthenticatorFactorStore(pool,keys,policy)` methods: `status(token:string)` returns `{active:boolean,version:number,recoveryCodesRemaining:number,available:boolean}`; `begin(a:Authority)` returns `{pendingToken:string,secret:string,uri:string,expiresAt:string}`; `activate(a:Authority,pendingToken:string,code:string)` and `regenerate(a:Authority)` return `{status:'changed',active:true,recoveryCodes:string[]}`; `remove(a:Authority)` returns `{status:'changed',active:false}`; `cancel(token:string,csrfToken:string,pendingToken:string):Promise<void>`.

Begin and activation require fresh password and, for replacement, fresh old-factor proof **each time**; starting consumes that proof but leaves the old factor active. Use `requirePasswordAuthority(...,'update')` before resolving the session, then re-resolve after child locks/expensive work. Activation also consumes the new-secret confirmation code for replay. Supersede earlier pending enrolments. Cancellation requires its exact live session/CSRF (proposal), changes no active factor. Only activation/regeneration emits raw recovery codes once. All successful active changes invalidate pending challenges and revoke every session together. Reset explicitly invalidates pending challenges while preserving active envelope, replay state and unused recovery hashes. Pending-session FKs plus cleanup exclusions must not create reverse account locking through cascades; prune no factor history without an approved retention policy.
