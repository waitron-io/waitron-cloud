# Send one Cloud invitation through the Stockholm SES sandbox

The owner said “yes to the trial” (19 November, campaign desk record `20261119-1848-K-amazon-email-trial.md`). On 21 November at 13:46 the watcher asked for “the first real email from the test Cloud to that mailbox”. The sender and sole human recipient are verified. The [previous plan](2026-11-19-test-cloud-amazon-ses.md) puts the invitation alongside a continuing startup switch. **Proposed change for watcher clearance.** Prove the invitation and feedback in one isolated run first. Leave the continuing switch and paired-box mail for a separate slice.

1. **One private run on the existing test host.** Use the reviewed Cloud image and a fresh throwaway PostgreSQL database with existing migrations and fresh mail keys. No public listeners or connection to the shared Cloud database. Leave [the ordinary email worker](../../../deploy/test-cloud/email-worker.mjs) on Mailpit. The bounded command lives in `deploy/test-cloud/ses-sandbox-proof.mjs`. It runs only from the isolated project and requires the expected empty outbox before seeding.
2. **Use the existing mail path.** Create synthetic handovers using `OwnerTransferStore.create` and the signed-account setup in `owner-transfer.test.ts`. Feed `EmailWorker.runOnce` one invitation at a time through `configuredAccountMailer`. Review private Stockholm authority separately from the bindings given to `configuredSesHandoff` and `configuredSesFeedbackConsumer`. Verify the provider inventory against `validateSesFeedbackPolicies`. Give the command only the bounded SMTP credential and temporary consumer credentials through private input. Keep the default country policy and all production entry points as they are.
3. **Prove the real path.** Send to the three named Amazon simulators first. Use `SesFeedbackWorker.runOnce` with a deadline to commit the matching delivery, bounce and complaint. Use a fresh synthetic business for each invitation and keep the same mail evidence and recipient keys. Try one fresh invitation to each blocked simulator and require a terminal refusal with no new provider attempt. Send one invitation to the verified mailbox after those checks. Ask the owner for inbox receipt and SPF, DKIM and DMARC results from the received source, with tokens and addresses removed. Stop on uncertain acceptance and check existing evidence before any decision to retry. Keep only redacted results and remove the disposable database and credentials from the host.
4. **Tests and size.** In `deploy/test-cloud/ses-sandbox-proof.test.mjs`, test refusal of nonisolated startup and an unapproved recipient, and stopping without a second send on an uncertain outcome. Reuse `ses-smtp-settlement.test.ts` for admitted attempt and provider receipt, `ses-feedback-cli.test.ts` for independent authority and `mail-handoff-suppression.test.ts` for refusal before transport. Expect 100–160 command lines and 60–95 test lines. Update the trial guide and backlog with the measured outcome. No AWS resource expansion, schema change, continuous worker switch, box relay or production sending request in this slice.
