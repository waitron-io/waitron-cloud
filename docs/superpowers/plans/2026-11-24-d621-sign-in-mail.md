# D621 sign-in mail in the machine-loss rehearsal

When a password request finishes on the server but the observer loses the reply, its email can arrive after a second request. The private rehearsal observer needs to wait for the message for the challenge it actually received. The existing confirmation endpoint must still accept the code before the observer records sign-in as recovered.

- In `scripts/kubernetes-services.mjs`, reuse the private test cell's primary lookup and PostgreSQL runner. For the received challenge, read its one sign-in outbox row by token digest and use its ID. The SMTP sender already uses this outbox ID in Message-ID. Read only the ID and delivery timing metadata. Keep the lookup inside the existing probe deadline and retain the current challenge through a lookup or inbox timeout.
- In `scripts/test-cloud-integration.mjs`, match that ID and the synthetic recipient in the private inbox before reading the code. The measured machine-loss path already uses its own account and inbox. Reuse that path and its existing confirmation request. Keep stage timings from the free comparison for password, database readiness, queued and sent mail, inbox read and confirmation. Identify the submitted message by ID in the trace without logging the code, token or mail body.
- Start with a failing case in `scripts/test-cloud-integration.test.mjs`. Lose the first password reply and deliver old and current mail together. Require the observer to send only the current code with the current challenge, and require it to surface a refusal as well as return success on an accepted reply. Keep the known-challenge wait and lost-confirmation tests. In `scripts/kubernetes-services.test.mjs`, check that the private adapter returns only the matching outbox ID and timings. Qualify the message-ID match once against the real private SMTP and inbox path. Run both named test files and `scripts/p1-observer.test.mjs`. Update the open qualification note in `docs/backlog.md`.

Reuse the existing measured-stops launcher, its signed-upload checks and independent cleanup. Keep the 90-second target and record the actual stage timings and cleanup. A pass would qualify this run. The earlier timeout lacks the stage data to attribute it to the stale-code retry.
