# Cloud action catalogue and controller implementation plan

> **For agentic workers:** After P1 lands and the owner approves this plan and its build, use `superpowers:executing-plans` inline, task by task. Read the TDD skill before writing implementation or tests. Use focused behavioral RED/minimal/GREEN cycles and signed-off commits. Do not dispatch subagents. The driver owns backlog updates, publication and `finish-branch`. This PLAN-only change authorises none of that work.

**Goal:** You can see what Cloud proposes, approve one precisely scoped action, and see its durable outcome without an alert, retry or lost reply granting broader authority.

**Architecture:** Keep one code catalogue and a country-owned PostgreSQL ledger for proposals, decisions, commands and operator notifications. The console reads and submits decisions to that authority; it never owns a second command ledger. Separate permission to initiate an action from the evidence and executor capability required to perform it. P4 supplies a working local controller with a synthetic executor and explicit unavailable production adapters.

## Review focus

1. A caller guesses a request/command ID in another country or cell, or loses operator authority during a lock wait. No private result or mutation escapes. Task 3 `operatorScopeAfterWait` and Task 8 `foreignIdsStayUnavailable`.
2. An approved command waits while policy reverts, evidence changes, proof expires or authority changes. Dispatch refuses the old decision. Task 6 `dispatchRevalidatesEveryBinding` and `reversionFencesQueuedAndOldWorker`.
3. Two processes race, a lease expires, or the executor acts just before its caller dies. One durable command identity survives; unknown completion never launches another dangerous attempt. Tasks 5/6 `expiredDispatchOnlyReconciles` and `crashAfterEffectDoesNotRepeat`.
4. Replayed/out-of-order C39 events or stale/unknown “recovery” arrive after approval. They cannot refresh evidence, close the incident or authorise work. Task 4 `signalReplayDoesNotRefreshEvidence` and Task 12 `unknownCannotClose`.
5. The sole owner's console or notification route disappears. Waiting remains visible; trading and routine services continue; customer opt-out cannot hide the operator request. Tasks 7/11 `operatorMailIgnoresVenuePreferences` and `consoleLossPreservesCountryLedger`.

## Catalogue and execution boundary

`catalogue.ts` exports the sole `actionCatalogue`. `CatalogueEntry={id:ActionId;targetKind:TargetKind;disruptive:boolean;startsWriter:'never'|'always'|'conditional';launchStatus:'ask-first'|'act-and-report';capability:'synthetic-only'|'unavailable';ownerChange:{sequence:number;record:string;incidentRefs:readonly string[]}}`. The owner record includes reversion; initial launch entries reference production sections 6/9 as their origin. Later status changes require a nonempty incident list and an owner-recorded repository reference. Runtime code validates structure and compares the installed digest; review establishes that the repository change was made/approved by the owner. Do not pretend a string proves authorship.

| Exact `ActionId` / target kind | Launch status | P4 execution capability |
| --- | --- | --- |
| `cloud.workload.restart_in_place` / `cloud_workload` | `act-and-report`, failed Cloud service only, same workload identity/location | `synthetic-only`; no Kubernetes binding yet |
| `machine.replace_failed` / `machine` | `act-and-report` initiation exception only | `unavailable`; never starts/reschedules a hosted writer |
| `hosted.workload.restart` / `hosted_venue`; `hosted.venue.move` / `hosted_venue` | `ask-first` | `unavailable`, P6 plus qualified joint contract |
| `machine.drain` / `machine`; `infrastructure.machine.add` / `cell`; `infrastructure.machine.resize` / `machine`; `cell.create` / `country` | `ask-first` | `unavailable`, coordinated infrastructure/placement integration |
| `country.failover` / `country` | `ask-first` | `unavailable`, P7 |
| `release.wave.expand` / `release`; `release.wave.pause` / `release`; `release.wave.resume` / `release` | `ask-first` | `unavailable`, P5 exact release/wave/cohort binding |
| `certificate.rotate` / `certificate`; `key.rotate` / `key`; `permission.change` / `permission`; `security.change` / `security_policy` | `ask-first` | `unavailable`; existing custody/support rules still apply |

`machine.replace_failed` is a permission to initiate a qualified machine workflow, not a provider adapter or authority to activate all workloads formerly on it. Mark `startsWriter='conditional'` for replacement/drain/failover and `'always'` for hosted restart/move; all other entries are `'never'`. Only authoritative current workload inventory can resolve `conditional` to no writers. Unknown inventory blocks it. P4 has no machine executor even for the no-writer case.

Set `disruptive=true` for Cloud workload restart, both hosted actions, machine replacement/drain/resize, infrastructure machine add, cell creation, country failover and release expansion/resume. Pause and certificate/key/permission/security actions use false; they still require their independent risk/authority gates and have no P4 executor. This flag controls cell capacity, not permission.

Routine certificate renewal under the existing issuer/name checks, authorised backup retries, gateway route reconciliation and capacity within an **already configured and bounded** machine group remain with their existing workers/platform controllers. They neither need P4 approval nor gain new authority from it. The design describes routine capacity but does not prove that today's code implements a production scaler. New groups/cells, resizing, increased limits/spend, data movement or an operation that can start a hosted writer use the catalogue and their separate gates. P4 does not create a scaler or turn “capacity” into an unlimited infrastructure action.

`cold.restore` is deliberately absent: its separate fresh-chain authority remains with the recovery implementation. Stop-proof refusal cannot select it. Trends can later propose catalogue actions, but P4 invents no capacity, spend, lead-time or monitoring threshold. A fresh alert may suggest investigation; it is not enough to select a failed runtime or prove its stop.

## Shared types and producer/consumer contracts

Task 1 defines the following in `types.ts`. `Id` means a validated UUID, `Utc` a canonical ISO UTC string and `Digest` a lowercase SHA-256 string. Type aliases do not perform validation. All external parsers reject extra fields, unknown versions, invalid times, empty scope, oversized strings and payloads over 16 KiB. Observation/event/decision timestamps cannot be ahead of trusted database time. Future deadlines are required where appropriate: evidence/proof validity, grant/approval expiry and command leases must be strictly after now at admission; equality means expired. Test these field-specific rules rather than rejecting every future timestamp.

`Scope={country:string;cellId:Id|null}` uses an uppercase country code; null denotes a country-level action, never a wildcard. `Target={kind:TargetKind;id:Id;uid:string;generation:string}` uses bounded 1–128-character private runtime identity/generation values. `TargetKind` is exactly the catalogue's target kinds. The target must belong to the scope in the authoritative reader; a caller-supplied country/cell pair is not that proof.

`Evidence={revision:number;digest:Digest;observedAt:Utc;validUntil:Utc;authorityRevision:number}` describes a freshly read, bound proposal snapshot. It includes the exact target, authoritative occurrence, source/configuration/placement generation, desired change and incident in its digest. `Proposal={version:1;requestId:Id;revision:number;occurrenceId:Id;action:ActionId;scope:Scope;target:Target;desiredDigest:Digest;incidentId:Id;source:{kind:'operator';id:Id}|{kind:'c39';id:Id};evidence:Evidence}`. No arbitrary command, shell text, provider URL, mail address or free-form repair instruction is accepted. `desiredDigest` binds an exact proposal document resolved by the trusted reader, including release/wave/cohort for future P5 use.

`RequestState='awaiting_approval'|'queued'|'blocked'|'dispatching'|'unknown'|'succeeded'|'failed'|'rejected'|'cancelled'`. `ActionRequest={proposal:Proposal;state:RequestState;policyDigest:Digest;version:number;blockReason:BlockReason|null;commandId:Id|null}`. `BlockReason='authority_unavailable'|'scope_changed'|'evidence_unknown'|'evidence_changed'|'proof_missing'|'proof_expired'|'profile_unqualified'|'policy_changed'|'approval_required'|'notification_unconfirmed'|'executor_unavailable'|'completion_unknown'`. Target replacement, removal or healthy evidence does not silently retarget a proposal; block/cancel it and preserve history.

`DecisionInput={id:Id;requestId:Id;proposalRevision:number;requestVersion:number;outcome:'approve'|'reject';policyDigest:Digest;evidenceDigest:Digest;expiresAt:Utc}`. `Decision` adds `operatorId:Id,grantRevision:number,decidedAt:Utc`. Approvals last at most 900 seconds in this local P4 design, with no renewal by polling; this is an implementation safety bound, not a C39 schedule or customer promise. The expiry and all evidence bindings are checked again at dispatch. A material change requires another visible proposal revision and decision.

`SafetySnapshot={occurrenceId:Id;scope:Scope;target:Target;desiredDigest:Digest;incidentId:Id;evidence:Evidence;condition:'adverse'|'healthy'|'unknown';writer:'none'|'new'|'unknown';profile:'synthetic'|'unqualified';stopProof:{state:'missing'|'unknown'|'current'|'expired';receiptRef:Id|null;authorityRevision:number|null;expiresAt:Utc|null}}`. `SafetyReader.read(proposal:Proposal):Promise<SafetySnapshot>` reads current authoritative evidence. The stop summary is an internal adapter result, **not** an invented signing schema or accepted A1018 receipt. Production's reader returns unqualified until the bilateral contract, owner approval and actual profile qualification exist. P4 accepts “current” only in synthetic contract tests; it ships no hosted execution adapter.

`Command={id:Id;requestId:Id;proposalRevision:number;scope:Scope;effectKey:Digest;claimId:Id;fence:number;leaseUntil:Utc;policyDigest:Digest;evidenceDigest:Digest}`. `effectKey` hashes version, action, country/cell, exact target UID/generation, authoritative `occurrenceId` and desired digest, independent of alert/notification/request retry IDs. The target-side reader supplies a stable occurrence ID for one confirmed failure or requested change; duplicate alerts and operator submissions cannot mint another one. After confirmed recovery, a genuinely new failure has a new authoritative occurrence and may create a new command even for the same workload UID. One occurrence/change keeps one command identity through retries. A changed target, occurrence or desired effect requires a different request; it cannot retarget an existing command. A `fence` is a monotonically increasing claim number that lets the recipient reject a stale claimant.

`Executor.execute(command:Command,proposal:Proposal,signal:AbortSignal):Promise<ExecutionResult>` and `Executor.reconcile(command:Command,signal:AbortSignal):Promise<ExecutionResult>` return `ExecutionResult={state:'succeeded'|'failed'|'unknown'|'not_started';receiptRef:Id|null}`. `not_started` is usable only from authoritative target-side reconciliation proving non-admission and fencing any old sender. An absent row, 404, timeout or dead endpoint means unknown. Receipt references expose no raw provider output. Unavailable executors never call a provider.

A request’s policy_digest is the projection of its current immutable proposal. A policy change never rewrites a proposal or past attempt: block pending work, append a visible proposal revision with the new digest, increment request version and obtain a fresh exact decision before handoff. Restart reads these stored bindings; it cannot substitute the current catalogue for the original authorisation.

Proposal/decision/command/event/outbox insertions are one transaction where specified below. Triggers reject cross-proposal decisions, malformed JSON, backwards revisions/fences, cleared dispatch markers, illegal state transitions and history mutation. Country/cell scope is enforced in every query, including by-ID reads; UUID secrecy is no defence. Cell inventory/target membership is checked through the trusted reader rather than inventing P3 tables or assuming every machine is a `remote_cell`.

## Country availability and integration handoff

The country ledger is the sole authority for a request, decision and command. A global console may aggregate observations with their source/time/unavailable marker, but writes go to the named country's authority and reads never establish a second actionable copy. Global console loss leaves requests and command identities intact. Unknown country authority blocks new admission; it does not revoke a venue already admitted by Waitron or halt ordinary on-prem trading.

During this transitional build, `OperatorAuthority` uses existing account/session/platform tables plus explicit country grants in the shared DB. It cannot claim to survive loss of a separately hosted global DB that does not yet exist. P3 must provide offline-verifiable sign-in/current operator authority and independent country storage before launch. Fail closed if that adapter is unavailable; keep existing country services/routine reconciliation independent. P4 introduces no global heartbeat into venue execution and no second database pretending to be P3.

Production integration still needs coordinated P1 packaging/secret/RBAC/replica tests, P3 authority/storage boundaries, an authenticated C39 adapter with the exact contract, D101 operator metadata/location qualification, D102 live delivery and D104 independent owner reachability. These are explicit follow-ups, not claims this local receipt satisfies them. P5 consumes catalogue decisions for exact waves later; P6/P7 supply their own qualified executors and writer/failover evidence. Do not add stubs that return success for unavailable capabilities.
