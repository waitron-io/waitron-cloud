# Require a trial or paid plan for guest menus

On the test Cloud, a venue can share its menu and guests can open the link once the venue has an active Connected or Hosted trial or paid level. The owner answered “Only with the trial” on 20 November at 14:13 in Lane K’s questions. This is slice 3 of setup pairing and works with boxes already connected. Lane D owns the box preview. Production rollout, pairing changes, payments and online ordering stay outside this slice.

## Build and prove the gate

- **Billing.** In `packages/registration/src/{venue-service-permissions,index}.ts`, expose a read-only venue-level lookup using the same UTC date, billing authority and `effectiveVenueLevel` as remote access. Scope the billing facts by organisation, business and venue. A test venue without billing authority is Registered. Read a consistent snapshot and leave expiry writes to their current callers. In `test/venue-service-permissions.test.ts`, prove that an active trial grants access and its end date removes it, without changing stored authority. Use the existing paid-level tests for Connected and Hosted.
- **Publish and enable.** In `packages/remote-access/src/guest-menu.ts` and `packages/account-http/src/{app,guest-menu}.ts`, check eligibility for `test-venue-levels` after box proof or owner and session checks. Hold the existing venue lock through enable and publish. Both return 403 `guest_menu_plan_required` when ineligible. Pass the same mode to the enable switch in `deploy/test-cloud/service-controls.mjs`. Withdrawal and takedown remain available. Add optional `planRequired: true` to the existing signed status reply when ineligible. Keep the actual stored state in that reply so old boxes can still withdraw. Lane D uses this field for the preview and publish refusal for a lapse after preview. In account-http `test/guest-menu.test.ts`, cover denial, successful publication on trial, and withdrawal and takedown while ineligible. Keep the free-publication case in legacy mode and use eligible fixtures wherever test-mode cases need to publish.
- **Serve.** In account-http `src/guest-menu-server.ts`, return the usual 404 on GET and HEAD for an ineligible test venue. Before sending buffered HTML, recheck eligibility and the existing state and revision. Keep the stored menu while the trial or plan is absent. It returns at the same link when eligible again if still shared. Withdrawal and takedown still remove it. Pass the mode from `src/server-cli.ts` and `deploy/test-cloud/account-worker.mjs`. In account-http `test/guest-menu-server.test.ts`, lapse the trial while the menu is buffered and assert no HTML is released. Use the Amazon worker’s guest case in `deploy/test-cloud/relay-runtime.test.mjs` to catch missed mode wiring, and `service-controls.test.mjs` to prove its switch refuses enable until eligible.
- **Explain.** In `apps/portal/src/{remote-controller,remote-screen,locale}.ts`, reuse the existing `connectedRequired` status. Explain that sharing requires a trial or plan and reuse Billing’s venue selection and **Start free trial** link when available. Otherwise link to Billing. Keep Stop sharing for a saved publication and hide Allow sharing while ineligible. If enable returns the plan refusal after a lapse, refresh the venue details. In `apps/portal/test/guest-menu-browser.test.ts`, check the reason, trial link and ability to stop sharing in English and Spanish, light and dark, at 390 and 1280 pixels.

Write each failing case first. Run the named files with `scripts/test-postgres.mjs` on the approved test runner, build the portal, inspect the browser captures and run `pnpm typecheck`. Update the guest-menu backlog, Waitron integration contract and affected operator guides. After test Cloud rollout is cleared, verify publication from a synthetic venue before and after starting its trial. Estimate 110–180 production lines and 130–190 test lines.
