# Cloud country flow enforcement implementation plan

> **For agentic workers:** Execute inline with `superpowers:executing-plans`, after the driver's fresh-context builder review. Read the TDD skill before writing code or tests. No delegation is prescribed by this plan.

**Goal:** Bind Cloud's existing placement, backup and mail boundaries to durable country decisions, denying unqualified destinations and reconciling late effects before any retry.

**Architecture:** Use PostgreSQL policy snapshots, destination bindings and an outside-effect journal. Admit work in short transactions, commit intent, call the adapter, then recheck before publishing or releasing credentials. Preserve existing service permissions and lifecycle evidence as independent requirements.

**Tech stack:** Node >=26, TypeScript, pnpm 9.15.0, handwritten PostgreSQL SQL, existing AWS SDK S3/STS 3.1136.0 and Nodemailer adapters.

**Spec:** [D101 sections 4, 6 and 8](../specs/2026-10-22-cloud-data-protection-design.md); [roadmap slice 5](2026-10-22-cloud-data-protection.md#slice-5-bind-placement-credentials-and-outbound-effects-to-policy). Source baseline: `2208befc414b6236bdbc8798082b433f7d0f01d4`, containing slices 1–4 and D451. This document is a plan, not implementation, qualification, review or acceptance evidence. Only local slice 5 is authorised; slices 6–12 are not.

## Constraints and decisions you must preserve

- `StorageLocation={endpoint,bucket,region}` describes an S3 destination. It is **not a Waitron location**. Introduce no Waitron location, protocol change or cross-repository work.
- Spain operational data/logs/keys remain `eu-south-2`; the additional encrypted backup is conditionally `eu-west-3`. No runtime failover, key replication, supplier qualification or Spain-outage recovery claim. Another country can have its own policy.
- Keep `spainCountryPolicy.flows=[]` and all production evidence unqualified. AI remains denied, even if a synthetic country flow permits its destination. No AI allow switch, live service, provider call, Docker run, deployment or fiscal allocation/hash/immutable-record change is authorised by this plan-writing task.
- Preserve every existing identity, ownership, lease, setup, plan, retention, verification, tenant-isolation and lifecycle assertion. No new plan mode, environment bypass, permissive default, test skipping or weakened previous-version receipt.
- `configurationRevision` remains the installation configuration counter. It is not a country-policy, placement, lifecycle, billing-permission, relay-grant or worker-claim revision. Existing increments, explicit reprovision, source-node identity and reader/key retention stay intact.
- No database transaction across a provider call. A session advisory lock for one canonical snapshot may span object I/O, as it already does, provided no transaction/authority row locks remain open. Unknown outcomes remain pending; recording a journal entry never authorises its effect.
- Every schema-bearing task uses handwritten new SQL and an appended manifest entry after live slot reconciliation; once any task ships, later tasks allocate another slot. Never edit previously shipped SQL.
- Resolve the open decisions below before enabling their affected paths. Independently landable tasks can deliver denied adapters and synthetic tests; that does not mean the complete slice or service is accepted.

### Lock and revision contract

1. Preserve authenticated account/session/membership locking where present. Service authority comes next: organisation `FOR SHARE`, venue `FOR SHARE` in legacy mode or `FOR NO KEY UPDATE` in venue mode, then billing authority `FOR UPDATE`. `readVenuePermissions` may acquire installation locks itself. Never call it for the first time from a location/job fence.
2. Installation locks precede location/cell locks. Add country-current-policy `FOR SHARE`, lifecycle `FOR UPDATE`, then destination binding `FOR SHARE` **after service admission and installation locking, before location/cell/job locks**. Setters use the same order and never acquire parent authority after country/lifecycle locks. Lifecycle request already locks venue then lifecycle; retain that order. Bulk exports materialise sorted organisations/venues and installations before sorted country/lifecycle/binding rows and cells.
3. Catalogue publication retains the session advisory `snapshot-publication:<captureId>` before its short authority transactions; preserve canonical-object exclusion, including connection discard on failure. Verification retains verification-policy then backup location, job, point, capture/key and attempt order; insert country/lifecycle admission before those locks, not in the final worker fence. Cleanup locks must also acquire parent permissions before location/job locks.
4. Remote keeps installation, move/cell and peer-key advisory locking in its current relative order. Relay keeps control, message advisory identity, account/grant/service authority, suppression and queue-row order; insert country/lifecycle checks after authority, before suppression/queue. Queue claim transactions do not take country locks and commit before admission. Email claim also commits before authority work; do not acquire account/venue authority while holding its claim row lock.
5. Re-read identities, destination, every independent revision and database `clock_timestamp()` after blocking locks and outside waits. Equal revisions after a downgrade/upgrade round trip are insufficient unless their namespace and identity also match. Do not use `Date.now()` as the lifecycle deadline authority.

## Review focus

1. A valid bucket hides unqualified envelope, telemetry, support or global-metadata processing: deny the whole outbound attempt (T1/T5).
2. Initial admission succeeds but policy, placement, lifecycle, identity or service permission changes during issuance: no secret/result publication; durable retirement survives restart (T2/T3).
3. A catalogue/worker/direct reader omits the optional caller fence, or uses another plan mode: intrinsic country checks still apply (T3/T6).
4. Source/target cell or asynchronous certificate/manifest publication changes underneath a move: no stale route becomes usable (T4).
5. A reply is lost, a claim expires, or an older database backup is restored: observe first, never reissue uncertain authority or erase previous-version proof (T2/T6).
