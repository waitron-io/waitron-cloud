# Paid venue email domain records

In Connected and Hosted test setup, a venue owner can save the address they want to send from, copy the one DNS alias their web administrator must add, and download the same email and remote-access records as a PDF. A tick shows that the alias points to the requested name. Staff email continues to use a Waitron From address. This is the first part of [Cloud slice 2b](2026-11-25-paid-venue-email-cloud.md#2b-show-verified-domain-records) in the [paid venue email design](../specs/2026-11-23-venue-email-paid-design.md).

## Save the address and show the records

- Extend `packages/account-http/src/venue-email.ts`, `app.ts` and `remote-access.ts`. Reuse the origin, request-forgery, test-owner, active-installation and paid-level checks. Add a registration migration for the sending address and a random DNS token on the venue. Keep the token when only the mailbox changes. Replace it when the domain changes. Use the token as the signing-key label at `<token>._domainkey.<venue-domain>` and in the target `<token>.mail.<configured-test-suffix>`. Enable setup only with that explicit test suffix. Clearing the choice or accepting an ownership transfer clears the address and token. Reuse the existing transfer update in `packages/registration/src/owner-transfer.ts`.
- Preserve `waitron_mail_reply_to` as the explicit reply address. In `packages/registration/src/relay-worker.ts`, use the sending address as the default reply address when no explicit one is saved. **Use standard sender** clears both choices. The existing test level and staff-grant checks still apply.
- In `apps/portal/src/{remote-screen,venue-email-screen,remote-controller,remote-types,api,locale}.ts`, use one list for the screen, copy buttons and PDF. Include the email alias and each configured remote-access name that differs from its assigned name. Keep the remote setup confirmation intact. Load `pdf-lib` when downloading and include a short note for the domain administrator.

## Check and test

- When setup opens or the owner refreshes, reuse the rate limiter and `boundedResolveCname` in `packages/remote-access/src/dns-lookup.ts`. Compare the exact normalised alias target. Return unknown for a timeout and unverified for a missing or different record. Check the same owner, installation and current choice again after lookup. Show the check for the current screen and choice only. The tick describes DNS delegation. The screen says sending from this domain is pending.
- Write failing cases first. Use `packages/registration/test/venue-service-relay.test.ts` for ownership, downgrade, save and reset, and a lookup completing after the choice changes. Check migration compatibility for old rows with no sending address. Use `apps/portal/test/venue-email-browser.test.ts` for screen, copy and PDF parity, including a remote custom name. Inspect English and Spanish, light and dark, at widths of 390 and 1280 pixels. Use `deploy/test-cloud/free-services-relay.test.mjs` in Mailpit to check Waitron From and explicit, default and cleared replies. Update `docs/backlog.md` and `docs/backlog/venue-email.md`.

The 25 November Stockholm sandbox verified the alias in one test DNS zone and sent no mail. A separate venue zone and delivered signatures still need qualification. Plan Amazon SES identity provisioning, key publication and cleanup after that evidence. The design's claim that keys can rotate without a venue DNS edit needs a safe cutover plan. Slice 2c owns actual sender selection and fallback.

**Estimate** 260–350 product lines and 140–200 test lines. Include the portal manifest and lockfile for the PDF dependency.
