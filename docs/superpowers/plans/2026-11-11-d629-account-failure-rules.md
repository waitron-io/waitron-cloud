## Decisions

- **Required configuration:** optional `CLOUD_ACCOUNT_FAILURE_RULES`, JSON with exactly `failureTargets` (all seven fixed groups: `health`, `account`, `installations`, `relay`, `portal`, `other`, `parser`) and `fast`/`slow` (each `windowMs`, `multiplier`). Every value is required when enabled; unset/empty disables only these rules. Failure targets are finite fractions in `(0,1]`, multipliers finite positive numbers, windows safe positive integer milliseconds at least the validated collection interval. Use a configured failure allowance directly, avoiding `1-successTarget` subtraction; no product-at-most-one restriction or fast/slow ordering check. Reject missing/unknown keys, malformed JSON and invalid values before listening, with a fixed setting-name diagnostic that hides values. Validate the collection interval first. `compose.yaml` forwards this optional variable only to the collector.
- **Calculation:** per group/window, bad share = increase in `server_error + timed_out` divided by increase across all four outcomes; refused requests contribute only to the denominator. Breached means share **≥** `failureTargets[group] × multiplier`; pin exact decimal boundaries such as `0.01×10` and `0.05×20`. This technical interpretation uses the configured failure allowance as “normal”, rather than learning a baseline. The trial supplies that value. This is a request-weighted rolling share, not a condition required at every poll. Timing/slowness rules are excluded.
- **Coverage and state:** timestamp when `collectRequests` resolves. For window W, use the latest same-process baseline in `[now−W−(intervalMs+timeoutMs),now−W]` and the current reading. Missing polls lose no cumulative counts: retain history through acquisition/operations failures, suppress current output while counts are unavailable, and recover immediately if a recent-enough baseline exists. Startup, zero requests or absent baseline is unknown; no healthy guess. Process-identity changes, counter decreases or backward time begin a new baseline; missing series count as zero. Prune samples older than the slowest configured window plus the allowance, retaining a preceding baseline as needed. Existing scheduled polling bounds memory by time; no second record-count cap, window upper bound, separate reset API, timer or durable store.
- **Interface/output:** create `deploy/local-stack/account-failure-rules.mjs`: `parseFailureRules(raw,intervalMs)` returns config or null; `createFailureRules(config,{intervalMs,timeoutMs})` returns `update(validatedSnapshot,nowMs)` with 14 `{group,rule,ready,breached}` rows (`breached:null` when unknown). `createCollection`/`serveCollection` take optional `failureRules`. Read account counts on every poll even when operations inspection fails, so account failures remain measurable during database outages. Give rule output its own successful-acquisition timestamp/freshness. Keep existing count/status suppression when operations collection fails. Export `waitron_cloud_account_failure_rule_ready{group,rule}` as 0/1, and `waitron_cloud_account_failure_rule_breached{group,rule}` only when ready; disabled emits neither. Failed/stale counts emit readiness0 without breach values. Labels are the seven fixed groups and `fast|slow`.
