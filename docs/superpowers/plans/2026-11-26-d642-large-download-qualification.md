# D642 · Qualify large downloads in Test Cloud

The [ranged route](2026-11-25-d642-ranged-download.md) is meant to let a test venue owner save a verified backup, key and manifest and open SQLite by streaming. This page covers the backup checker and browser memory work. Keep downloads at 16 MiB until both pass and the HTTPS rehearsal succeeds. [Owner’s exit design](../specs/2026-10-29-cloud-billing-design.md#8-cancelling-lapsing-and-closing-an-account)

## Verify a 512 MiB backup on the LAN worker

In a disposable Linux checkout set `deploy/backup-verifier/streamed-target.json` to the generated target for Waitron `71daa2410af1c50c3a23429596ae0fb0ef62f552`, already pinned for the Amazon test build. Build with `node scripts/build-backup-verifier.mjs --streamed` and set the disposable database policy to that target and image. That runs the LAN worker’s own revision check. Use the existing 1 GiB memory limit, 16 GiB private verifier scratch and 5 GiB worker stage. The released Waitron fix previously passed on a 375,215,594-byte archive. [Scratch and policy](../../backup-verifier-containment.md#use-a-private-disk-for-the-venue-level-trial) · [Waitron fix](https://github.com/clintongormley/waitron/pull/3731)

Use the matching Waitron writer. Seed synthetic print jobs and tune the final payload until the ordinary compressed capture is 536,870,912 bytes. Record its expanded SQLite size. Publish through the local upload path and run `deploy/test-cloud/backup-worker.mjs --once` against the selected job. Reuse the assertions in `deploy/test-cloud/test-fixtures/integration-verification-evidence.mjs` for the verified point, size, digest and child cleanup. Confirm both disk stages clear. Run a corrupt-copy control and replay a retained small fixture from the old pin before promoting the new pin. If either the ceiling or the retained copy fails, record the stage and verdict and bring the smallest correction to the watcher. Run `scripts/build-backup-verifier.test.mjs` and update `docs/backup-verifier-containment.md` and `docs/backlog/data-lifecycle.md` with the measured result. Keep the Linux replay as a lane receipt. Estimate 24 generated pin lines, up to 30 product lines if a Cloud fix is needed and up to 30 focused test lines for that fix.

## Isolate and fix browser memory growth

Reproduce the matched loopback with the same fixtures and 4 MiB replies. Compare fetch and drain without disk writes, writing the same chunks without fetch, and opening staged archives with fresh profiles. Attribute peaks by browser process and record idle and phase-start readings. If local opening grows, compare heap snapshots or forced collection where supported and isolate the binary copy loops in `apps/portal/src/backup-download-worker.ts`. Keep one changed variable per run.

Fix the measured cause and run `apps/portal/test/backup-download-worker.test.ts` for shared opening changes. Save any range-only fix and its replay in the lane receipt for slice C. Take a server or browser-engine limitation back to the watcher. For release evidence, rerun three repeats per size in Chromium, Firefox and WebKit with matched SQLite lengths, the original sampling method and the unchanged repeat-spread rule. Require matching archive and database checksums and a valid authentication tag. Estimate up to 50 product and 50 test lines for a shared fix.

Lane J can run both checks with the released Waitron source in its disposable environment. A shared test box upgrade is outside this plan.
