## Verify a 512 MiB backup on Linux

Start with the existing `--amazon-test` verifier image recipe on isolated local Linux. Its pinned Waitron revision includes the print-table sort fix, and the older LAN pin predates it. The fix was measured on a 375,215,594-byte archive. Set the image and matching policy in a disposable venue-level worker with the existing 1 GiB memory limit, 16 GiB private verifier scratch and separate 5 GiB worker stage. [Image pin](../../../deploy/backup-verifier/amazon-test-target.json) · [Scratch and policy](../../backup-verifier-containment.md#use-a-private-disk-for-the-venue-level-trial) · [Waitron fix](https://github.com/clintongormley/waitron/pull/3731)

Use the Waitron writer for a synthetic 536,870,912-byte archive and publish it through the local archive path. Drain the selected job through `deploy/test-cloud/backup-worker.mjs` and read the catalogue’s verified point, size and digest. Use a corrupt copy of the same size as a refusal control. Check that its job finishes without admitting it and that the child and both stages are cleaned up after each run. Reuse `deploy/test-cloud/test-fixtures/integration-verifier.mjs` and `integration-verification-evidence.mjs` for the worker and receipt checks. Record the failing step and resource readings before changing anything. If the LAN worker needs the fixed pin, update `deploy/backup-verifier/streamed-target.json`, check matching and stale images, and recheck a retained small backup on the new pin. Keep the existing limits, verification checks and provider configuration. Expect 0–30 product lines, about 24 generated lines if repinned and up to 70 test lines.

## Isolate and fix browser memory growth

The matched loopback run passed all 18 SQLite checksums. Chromium exceeded the gate in transfer and authentication, and WebKit exceeded it in all three phases. Reproduce with the same fixtures and 4 MiB replies. Measure owned browser processes in bytes at regular intervals and phase boundaries. Compare fetch and drain without disk writes, disk writes of the same chunks without fetch, and opening already staged archives in fresh profiles. Use phase-start readings to distinguish memory carried over from the preceding phase. Change one thing per run.

Fix the measured cause in `apps/portal/src/backup-download-worker.ts` or `backup-download-bytes.ts` if it is in shared opening code. Prove any range-only change in the loopback and carry it into slice C. `apps/portal/test/backup-download-worker.test.ts` owns authentication, extraction and cleanup, `backup-transport-boundary.test.ts` owns malformed replies, and `backup-browser.test.ts` owns the saved database. Rerun three repeats per size in Chromium, Firefox and WebKit with matched expanded SQLite lengths. Require matching archive and SQLite checksums, a valid authentication tag, and each phase’s median increase above idle within the larger repeat spread. Keep diagnostics outside the repository. Expect up to 50 product and 50 test lines before slice C.
