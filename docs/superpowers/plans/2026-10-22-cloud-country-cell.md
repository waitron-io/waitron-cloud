# P1: A country cell on Kubernetes implementation plan

> **For agentic workers:** Use `superpowers:executing-plans` for the authorised inline execution, task by task. Read the TDD skill before writing implementation or tests. Do not spawn agents or ask the owner to choose execution again. The driver reviews and lands this documentation milestone before implementation; this milestone changes documentation only.

**Goal:** Package today's Cloud services, deploy them through an in-cluster repository reconciler, and prove that a genuine synthetic venue retains sign-in, remote access and backups through the loss of each of three local Kubernetes nodes.

**Architecture:** Use Flux, three schedulable kind control-plane nodes, synchronous PostgreSQL replication and a distributed local S3 rehearsal store. Run multiple Cloud workers against their existing database claims; use one elected gateway with two standby candidates so TCP and WireGuard reach the same tunnel. The current shared account/venue database remains transitional: this is neither P3's global/country separation nor a production-ready deployment.

**Tech stack:** Node 26.11.1, pnpm 9.15.0, kind 0.31.0, Kubernetes/kubectl 1.34.3, Flux 2.8.0, CloudNativePG 1.29.2 and PostgreSQL 18.4. Initial pins are source/compatibility checked below; Task 1 locks digests/checksums and Tasks 4–12 qualify actual execution, rather than claiming these versions have already been rehearsed together.

**Spec:** [Approved design](../specs/2026-10-22-cloud-production-deployment-design.md), especially §§3, 4, 6, 9, 10, 12; [seven-plan order](2026-10-22-cloud-production-deployment.md); [documentation ownership](../../documentation-ownership.md). Read all three before execution.

## Review focus

1. A killed database primary must not lose an acknowledged account, pairing, key or job; the two surviving nodes must accept writes (Task 5 `primary_loss_preserves_commits`, Task 12).
2. A gateway handover must keep TCP and UDP on one active tunnel and retain endpoint/key identity, including certificate replacement with unchanged routes (Tasks 8/9 `same_routes_new_certificate`, `lease_loss_closes_tunnel`, Task 12).
3. A killed verifier/worker or broken Docker daemon must leave uncertain snapshots pending and reclaim claims, never fabricate a successful restore (Task 10 `daemon_loss_no_verdict`, Task 12).
4. A missing secret, migration or reconciler must fail visibly, without generating replacement keys or leaving an apparently healthy empty-route gateway (Tasks 3/4/8 and Task 13 omission tests).
5. Partial creation, low memory or interrupted cleanup must affect only recorded owned resources and must not produce a passing receipt with skipped phases (Tasks 1/12/13).

## Acceptance and boundaries

“Survives a node loss” means bounded service recovery with durable state, not zero lost in-flight connections. Inject an abrupt `SIGKILL` into exactly one recorded kind node container, with its disks and every workload unavailable for **900 seconds**. Exercise each node separately; restore full replication and health before the next leg. This models a stopped machine, not a network partition, permanent disk destruction, real AZ, host/Docker-VM loss or regional failure.

| Path | Required measured behavior in each leg |
| --- | --- |
| Sign-in | Existing sessions remain valid; new password sign-in and one fresh email-assisted signup complete within 90 s of fault injection. Probe the existing session every 5 s and new password sign-in every 60 s after recovery. Preserve accounts, sessions, factor/email/issuer keys and pairing. |
| Remote access | Stable hostname, gateway endpoint and public key; a fresh verified staff HTTPS connection and allowed public request succeed within 90 s, then every 5 s through the genuine WireGuard tunnel. The venue process never restarts. Existing TCP/WebSocket sessions may disconnect and reconnect. |
| Backups | Previously acknowledged object bytes, digests, catalogue rows and keys remain readable throughout retries; a new real capture/upload/catalogue completion and genuine v1 restore verification finish within 300 s, then another completes while the node stays off. Retry interrupted transfers using existing capture identifiers; do not invent transparent resumption. |
| Reconciliation | A changed repository revision and deliberate Cloud Deployment drift reconcile within 180 s while the node remains off, including when the lost node hosted Flux or the database operator. |

Use monotonic timing, 5 s request deadlines, 1 s sampling, and record every failure, retry and longest success gap from the last pre-fault success. A 90/300 s recovery bound does not permit repeated later outages: after first recovery require all scheduled probes to succeed for the rest of that leg. Infrastructure loss may interrupt a pending operation, but no acknowledged durable state may disappear. A missed bound fails P1; do not widen it to fit a run or describe the result as uninterrupted availability. These are provisional engineering rehearsal targets, not customer promises or proof of literal zero-outage availability. Retain the approved design's stronger wording as a separate launch qualification requirement; do not rewrite it from this experiment.

All probe traffic uses a central rolling-window budget across setup and all fault legs, including every actual retry. Initial new-login/signup attempts may run at 0/15/30/45/60/75 s only while below the unchanged limits; after recovery use the cadence above, with only one signup journey per leg. Keep at most 8 login attempts per source IP/60 s, 24 per email/900 s and 8 signup request/complete attempts per IP/900 s, reserving the remaining allowance for setup and ordinary flow. Count source identities after the real proxy mapping, assuming the same client/IP rather than inventing one per request. An exhausted budget fails the schedule before injection; never skip a mandatory probe, reset limiter rows, raise a limit, or report a policy refusal as healthy. Record all scheduled and attempted operations.
