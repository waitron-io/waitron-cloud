# D621 email delivery after a database connection drops

A surviving worker should send fresh sign-in mail after it reconnects to PostgreSQL. In the free Kind rehearsal both workers exited on idle connection loss. The first fresh message spent 31.234 seconds queued after the database could take writes, including 26.621 seconds with both workers down. The other 4.613 seconds covered failed startup checks still in progress and the final startup and send. Kubernetes reported 10- and 20-second restart delays. The earlier 49.716-second delivery lacks precise restart times. The earlier 76.450-second delivery followed deliberate submission at 75 seconds and took 0.271 seconds from queue to send. The experiment cannot show whether Stockholm's workers exited, hung or stopped polling.

Retry rejected passes through `runWorkerLoop` and its one-second wait. Include the existing database, key and mail configuration hint in retry logs. Set the pool's client-side query timeout to 11 seconds so silent connections also release their slots. During shutdown keep failures fatal. Leave `--once`, `--status`, claims, the 60-second lease, mail retry rules, probes, the test-Cloud worker, monitor and usage out of this slice.
- In `packages/registration/src/email-outbox.ts`, run the existing `checkConsumerSchema` in the claim transaction the first time each connection is used to claim mail. Use the module path from `cloud-action-cli.ts`. Log a fixed schema refusal and exit 1 when a claim encounters an incompatible migration ledger. Let accepted sends record their outcome. The watcher cleared the claim-only check at 18:21 on 24 November after both reviews reproduced duplicate delivery with the pool-wide check.
