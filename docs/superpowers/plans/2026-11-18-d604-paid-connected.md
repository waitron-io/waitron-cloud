# D604 test plan for paid Connected

On a local Cloud, a verified synthetic owner can see the price for one test venue, confirm a first-month payment with a saved SumUp sandbox card, and see the paid dates after success. Rehearse with one business, one venue and a throwaway database. This is part of [billing plan row F](2026-10-29-cloud-billing.md#the-slices-in-order), in the scope the watcher set on 18 November at 17:35.

- [ ] **Quote and reserve.** In `packages/account-http/src/billing-account.ts`, use the published price, `chargeTotals`, `nextRenewalAfter` and the existing UTC test calendar for the EUR subtotal, VAT, total and dates. Consent binds the price, business and venue revisions, total and start date. Recheck these, the card and single-venue test scope under the business lock before writes, including UTC day rollover. Require a positive price, Registered status and no previous anchor, paid period or trial. Keep the free trial available before payment and explain that paying uses it up. Refuse trial start while a first payment is pending or unresolved, under the same lock.

- [ ] **Freeze one line.** Extend `packages/registration/src/billing-{types,store,payments}.ts` and `src/index.ts`. A `freeze_initial_connected` command stores an existing renewal-kind charge containing exactly one Connected line, using the agreed amount and exclusive next-month end. Create the default Registered billing row if absent. Leave the venue level, its Connected start and all hosted allocations as they were. Commit the freeze and `begin_attempt` together with separate stable event keys within the business. Only the request that creates the attempt can send payment. Reuse the record on reload, concurrent consent or a new date.

- [ ] **Charge once and settle by reading.** In `packages/account-http/src/billing-connected.ts`, `app.ts`, `billing-methods.ts` and `billing-method-providers.ts`, expose consent and refresh only in new explicit `CLOUD_BILLING_METHODS_MODE=test-with-first-charge` with the existing test-account, venue-mode and owner checks. Reuse the method setup's fresh sign-in proof for charging and recheck it before writes. Use the saved sandbox key and require read-only `/me` to confirm `extdev: true` and the configured merchant before each write. The method and attempt must match that merchant. Create once with the attempt's request key as the checkout reference, commit the verified checkout ID, then process once with PUT and the saved token. Send the frozen cents as euros. Keep database transactions closed across provider calls. Refresh can only read by the stored ID or, after a lost creation reply, by the stored reference. Settle only a bound checkout after a `PAID` read matches its ID, reference, merchant, customer, amount and currency. Pending or uncertain results allow status refresh only. A verified decline or payment challenge ends the rehearsal. In one guarded transaction, record success and the paid period, set the initial anchor, and enable Connected with `BillingStore.transitionOn`. A later refresh keeps the dates agreed at consent.

- [ ] **Show the result and reset after the rehearsal.** Extend `apps/portal/src/billing-{types,controller,screen}.ts`, `locale.ts` and `api.ts`. Confirm the test total including VAT and dates, keep pending separate from paid on reload, and offer a status refresh. Show the paid-through date. Existing test service authority continues until the throwaway environment is reset. Document the teardown and how to seed a past-dated synthetic price with `BillingPriceStore.publish` in `packages/account-http/README.md`. Update the Subscriptions and billing entry in `docs/backlog.md`.

- [ ] **Test first.** Run `packages/registration/test/billing-payments.test.ts` and `packages/account-http/test/billing-connected.test.ts` through `node scripts/test-postgres.mjs exec node --test` for the frozen line, normal renewals, quote and trial refusal, scoped one-attempt concurrency, lost replies and atomic success. Run the existing `billing-method-client.test.ts` and `billing-method-config.test.ts` for opt-in, live/wrong merchant with zero writes, and exact test authorization and amount on writes. Run portal `billing-api.test.ts`, `billing-account-fencing.test.ts` and `billing-browser.test.ts` for consent, pending reload, free trial and stale replies. Inspect both languages and themes at 390/1280, then run `pnpm portal:build` and `pnpm typecheck`. After those pass, Lane K runs one sandbox rehearsal using D604's test-only credentials, records a sanitized receipt and removes the throwaway environment.
