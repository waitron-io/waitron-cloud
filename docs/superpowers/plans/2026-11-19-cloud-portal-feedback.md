# Portal changes from the Juniper trial

After pairing on the box, an owner sees the venue’s own name, can remove an old connection, and can reach the right controls from shorter Account and Venues pages. Remote access offers the eligible venue a Connected trial and shows actions that match its current state. The finish line is a page check of all four points on the Amazon test Cloud. Confirm a test Cloud update window with the watcher before touching the shared setup. Use synthetic data and the existing host and resources.

1. **Use the name the box sent.** Add nullable `venues.display_name` in `packages/registration/migrations/077_portal_venue_feedback.sql`. Backfill the latest retained successful named pairing that matches the venue and its current installation. `packages/registration/src/pairing.ts` copies the signed name from the saved request at fresh completion in the existing transaction. Completed retries and nameless requests leave the name alone. `packages/account-http/src/venue-overview.ts` adds it to the scoped account view. Keep machine replies and signing unchanged. Register the migration in `packages/registration/src/migrate.ts` and preserve the historical checks when moving the current migration count and tail assertions.

2. **Remove a stopped connection.** Add nullable `installations.portal_removed_at` in the same migration. Keep **Stop Cloud access** for active connections, then offer **Remove venue** to owners of stopped connections. Extend `packages/account-http/src/installations.ts` and `packages/registration/src/installations.ts` with an account-only write for the exact installation. Reuse the owner scope, Origin and CSRF checks. After locking, recheck the session and the current stopped row in the authorised venue. Reject a venue that still shares a public menu and point the owner to **Stop sharing**. Use the existing venue-before-installation lock order used by guest menu writes. Retrying an accepted removal succeeds. Keep venue, backups, recovery, billing and audit records. A replacement connection appears on the list.

3. **Show the useful parts first.** In `apps/portal/src/installation-screen.ts`, show the name and connection status, using translated **Venue** and a short ID for legacy rows without names. Keep backup, monitoring and other actions in labelled disclosures. Filter removed connections from Venues and Remote access, including the organisation chooser and empty state. Keep recovery’s existing list. Use the existing inline confirmation pattern with clear cancel and confirm actions. Explain what disappears and that stored backups and billing continue. Extend `installation-controller.ts`, `installation-types.ts` and `api.ts` with a validated, account-bound removal reply. In `screens.ts` and `account-security-screen.ts`, collapse secondary Account sections, keep enrolment visible and reveal the relevant section for links and emailed confirmations. Put concise English and Spanish labels in `locale.ts`.

4. **Offer the right Remote access actions.** Move the existing per-venue **Start free trial** link in `remote-screen.ts` where eligible owners can see it before opening setup. Keep the explicit Billing opt-in and the selected venue. Show **Stop sharing** only for a shared menu and **Allow sharing** only for a blocked menu. Use a label for closing the open panel that describes that action. `RemoteController.close()` closes the panel. The venue’s access does not change. Registered venues keep their basic services.
