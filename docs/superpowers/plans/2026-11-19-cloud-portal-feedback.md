# Portal changes from the Juniper trial

An owner sees the name sent by the box, can remove an active or stopped connection, and sees shorter Account and Venues pages. Remote access offers eligible venues a trial and shows menu and panel actions that match their state. Account and guest-menu pages open when browsing between them. Check these outcomes on a synthetic venue on the Amazon test Cloud.

1. **Name the venue.** Register `077_portal_venue_feedback.sql` in `packages/registration/src/migrate.ts`. Add nullable `venues.display_name` and backfill from successful named pairing requests still retained for the current installation. In `pairing.ts`, save the signed name at fresh successful completion. Retries and nameless pairings preserve it. Return it through the scoped `packages/account-http/src/venue-overview.ts`. Use translated **Venue** and a short ID if no name was ever saved or can be recovered from history. Check a fresh named synthetic pairing if the existing test pairing has lost its name.

2. **Remove a connection in one step.** In `packages/registration/src/installations.ts` reuse the owner revocation transaction for removal, with nullable `installations.portal_removed_at` in the same migration. The account-only **Remove venue** action in `packages/account-http/src/installations.ts` stops and hides an active connection, or hides an already stopped one. Keep the existing stop-only action. Require the owner, Origin and CSRF. Lock the venue before the installation for removal and recheck the current installation, authority and session before writing. A shared menu must be stopped first. Keep the menu controls open after refresh for an already-stopped venue, and close stale remote controls when revocation or removal is newly observed. Preserve the existing revocation audit and add no event for hiding a stopped connection. Make removal retries safe. A replacement appears normally. Explain in the confirmation that local trading continues, stored backups stay, and Billing still lists the venue and any continuing charges.

3. **Shorten the pages.** In `apps/portal/src/installation-screen.ts` remove repeated rows and copy, sort the named cards by venue name and use at most one **Details** disclosure per card. Keep primary actions visible and explain where to add a venue. Return the removal flag in the account list so `installation-controller.ts` can filter the two portal lists and their chooser while Recovery keeps its list. Validate both the list and removal replies in `installation-types.ts` and `api.ts`, and reuse account-switch checks. In `screens.ts`, `account-security-screen.ts` and `app.ts`, collapse secondary Account sections and reveal controls when needed for security links, passkey feedback or an emailed confirmation. Keep enrollment actions visible. Use concise English and Spanish in `locale.ts`.

4. **Match the Remote access actions to the venue.** In `remote-screen.ts` offer the existing trial link before setup only for a registered, eligible venue with a current, non-revoked connection. Keep explicit opt-in for the selected venue and keep Registered basics. **Stop sharing** appears for a shared menu and **Allow sharing** for a blocked menu. The empty state offers no sharing action. **Close details** closes an open panel.

5. **Let browsers recover from a reused connection.** Chromium reproduced the two 403s with ordinary navigation between the two names on one HTTP/2 connection. In `deploy/test-cloud/proxy.amazon.cfg` return 421 for HTTP/2 requests crossing between the configured account and menu hostnames on the wrong TLS connection. Place this in the guest-host block before the existing name check. Keep the existing 403 rules for other authorities and for HTTP/1. Extend the two-host fixture in `deploy/test-cloud/proxy-proof.test.mjs` to assert HTTP/2 negotiation, 421 and correctly addressed 200s in both directions. Replay both browser navigation orders once in a separate disposable browser fixture.
