# Slow down bulk Cloud sign-up

People can still request a confirmation email and set a password from its link. Cloud checks the browser before each sign-up or password-reset email request, limits bulk sign-up and warns the operator about unusual volume. This implements Lane J’s SIGNUP-ABUSE queue entry and the owner’s limits recorded by the watcher on 24 November at 21:24.

1. **Check the browser once per request.** Move the signed proof and worker from `packages/remote-access/src/public-gate.ts` to `browser-puzzle.ts` beside it and export the shared helper. Keep the public-page access cookie and forwarding behavior. In `packages/account-http/src/app.ts`, issue a short-lived challenge for the form and bind it to the exact client address resolved through `client-address.ts`. Keep the existing Host, Origin and body checks. Verify the proof and spend a single use in the existing `account_rate_limits` table across API instances. Test that a missing, expired, wrong-address or wrong-form proof queues no mail, and that concurrent submissions of the same proof allow just one. Keep the existing `public-gate.test.ts` and `public-gate-guidance.test.ts` checks.
2. **Limit requests and emails.** Set five sign-up requests per connection per hour in `app.ts` and leave password-reset allowances alone. One IPv6 /64 counts as one connection for limits. In `packages/registration/src/signup.ts`, reuse the per-email transaction lock and indexed request history to allow three confirmation emails per normalized address per UTC day with at least five minutes between sends. Keep the same generic email acknowledgment when suppressing a send. In `account-http.test.ts` verify the sixth request is refused across an IPv6 /64. In `signup.test.ts` check the outbox for the resend gap, daily cap and recovery after the window resets.

People can request on Wi-Fi and open the link over mobile data. Exempt exact matches on the configurable public-provider list, initially Gmail, Outlook, Hotmail, Yahoo and iCloud’s `.com` domains. Count the accepted creation and claim the one warning in the same transaction, then write a structured warning with the UTC date to the account service log after commit. The 11th creation triggers the warning and subsequent eligible creations proceed. Test competing completions for the last place, failed or duplicate completion leaving allowances intact, the domain exemption and rollover, and one warning without a global refusal. Reuse the existing tables.

Extend `signup-reset-acknowledgement-browser.test.ts` for fresh proofs and `journey.test.ts` for verified mail and reset through Mailpit.
