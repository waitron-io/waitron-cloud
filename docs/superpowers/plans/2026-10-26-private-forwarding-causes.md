# Private public-forwarding causes (D291) implementation plan

**Goal:** You can inspect the latest known gateway forwarding outcome for your venue in Account without exposing private upstream information to visitors.

**Architecture:** Add optional, authenticated gateway reports, collect them inside the country and read a short-lived latest observation through the existing owner-only remote status request. Keep outside probes, installation-reported service health and gateway forwarding outcomes separate. Reports describe an observed attempt, never the present availability of every visitor's page.

**Tech Stack:** Existing Node >=26, TypeScript, node:crypto Ed25519, node:https, PostgreSQL/pg, Hono, Lit, pnpm 9.15.0, node:test and Playwright; no new dependency or public endpoint.

**Spec/reference sources:** Owner's planning authorisation, 2026-10-26 07:32, quoted below; `docs/refusal-self-service-audit.md` R9; `docs/backlog.md` D254/R9; `docs/documentation-ownership.md`; `docs/superpowers/specs/2026-10-22-cloud-production-deployment-design.md` §§3/4/12; `docs/superpowers/plans/2026-10-22-cloud-{production-deployment,country-cell,global-country-split}.md`; `docs/country-policy.md`. These references supply boundaries, not D291 build authority.

- **Owner constraint:** No fiscal behaviour changes, global customer access, grants, activation authority, repair controls, provider deployment, spending or customer messages. Preserve country isolation and the one-owner direction; do not broaden today's membership model. No public/live service exists.
- **Read evidence:** `packages/remote-access/src/public-gate.ts:89–99` forwards only after host/proof/limits pass. It uses a **5,000 ms socket inactivity timeout**, a **65,536-byte response cap**, no redirects and an exact upstream **200** requirement. Request/response errors, explicit timeout/limit destruction, client cancellation and completed non-200 responses converge on visitor 503 and `unavailable++`. ## Proposed design and defaults for approval

**Alternatives:** Reusing probe or installation observations would assign the wrong producer and meaning. Reading only gateway RAM would lose evidence on restart and differ across Account replicas. An HTTP ingestion service adds network authority unnecessarily. **Recommend a signed private file plus country-local collector**, matching the existing file delivery model, with a new transient SQL store so Account replicas agree.

### Outcomes and public behaviour

| Fixed `ForwardCause` | Exact meaning and English / Spanish explanation |
| --- | --- |
| `upstream_non_200` | A response ended normally with an explicit status other than 200. “The venue application returned an unsuccessful response.” / “La aplicación del local devolvió una respuesta no satisfactoria.” Application 403/404/503 are **not** proof of a Cloud route fault. Do not retain their status or body. |
| `upstream_timeout` | The existing request timeout event fired. “The connection to the venue application timed out.” / “Se agotó el tiempo de conexión con la aplicación del local.” Do not describe this as a total request deadline. |
| `upstream_response_limit` | The existing response byte cap caused destruction. “The venue application response exceeded the gateway limit.” / “La respuesta de la aplicación del local superó el límite de la pasarela.” |
| `upstream_transport` | Request/response error, aborted response or premature response close without a preceding locally identified timeout, size limit or client cancellation. Includes TLS/socket failures; no finer diagnosis from error text. “The gateway could not complete the connection to the venue application.” / “La pasarela no pudo completar la conexión con la aplicación del local.” |
| `forward_internal` | A synchronous request-construction or other internal forwarding exception, or a missing response status. “The gateway could not complete this forwarding attempt.” / “La pasarela no pudo completar este intento de conexión.” Do not label arbitrary throws as transport faults. |

Successful upstream 200 completion produces `category:null`, clearing the previous failure through a newer observation. Visitor disconnect suppresses reporting for that attempt, including later socket errors; it establishes no venue fault. Local host/proof/path/method/body/quota refusals produce **no forward observation**. Outside probe failures remain outside reachability evidence in Alerts. Preserve every public status, negotiated EN/ES body, header, retry link, counter, quota and credential-stripping assertion, including existing cancellation counting.

### Delivery, schema, retention and loss

- New `forward-report-writer.ts`: `ForwardReportWriter.begin(binding:ForwardBinding,startedAt:number):((category:ForwardCause|null,observedAt:number)=>void)` and `flush(now:number):Promise<void>`. Wire through `gateway-cli.ts` using opt-in `GATEWAY_FORWARD_REPORT_KEY` and `GATEWAY_FORWARD_REPORT_DIR`, both absent by default. Provision an absolute, dedicated country-local directory excluded from backups: mode **2750**, owned by the writer with a dedicated collector group (deployment GID **1000**); reports are **0640** and inherit that group. Only writer/collector mount it; collector mount is read-only. Keep the **0600** signing key outside that mount. This permits the root gateway and nonroot collector without granting either new capabilities. Native fixtures use their own UID/GID. Wrong identity, permissions or unavailable storage disables diagnostics only; `status.json` stays aggregate-only.
- Pin writer construction as `constructor(options:{directory:string,key:KeyObject,cellId:string,gatewayId:string,generation:number,readerGid:number,now?:()=>number})` and `restore(now:number):Promise<void>`. Instantiate/restore only after matching v2 authority is applied, before accepting observations; reload or disable on generation changes. `readerGid` defaults to 1000 in CLI wiring; require a pre-provisioned directory with the exact writer UID and group, rather than changing runtime capabilities or granting broad volume access.
- Coalesce one latest completion per route, maximum **64 entries**, no visitor queue or append-only history. Flush at most once per **30 seconds**, one signed latest `report.json` using fsync/rename; maximum **256 KiB** including envelope, plus one owned temporary file. Allocate a larger persistent report sequence only with that atomic snapshot; newly changed entries receive that sequence as `observationSequence`, unchanged entries keep theirs. At most two file publications/minute; flush expiry removals on the same cadence. Reject extra routes instead of growing a queue.
- Restore verified local sequence/state on restart, retaining original timestamps/expiry and never refreshing evidence by replay. For an expired signed snapshot, validate its signature/shape at its signed `issuedAt`, recover its sequence and last publication time, and discard expired observations. A marker bound to gateway/generation distinguishes first use from lost state; absent/corrupt state after initialisation disables reporting until trusted generation rotation explicitly permits a fresh stream. A crash can lose up to one unflushed 30-second window. Restore the 30-second publication spacing too; no shutdown flush bypasses it. No disk backlog or transport retry queue exists.
- New `forward-report-collector.ts` exports `collectForwardReport(mapping:ForwardReportMapping,store:ForwardObservationStore,now?:number):Promise<void>`, with `ForwardReportMapping={country:'ES',environment:'test'|'production',cellId:string,file:string,writerUid:number,readerGid:number}` from trusted local configuration, never a request. New `forward-report-cli.ts` takes one absolute config path and optional `--once`; uses `DATABASE_URL`, polls each mapping every **30 seconds**, one in flight per cell, pool max **2**, connection/statement bounds **5 seconds**. Files must be regular, at the exact mapped path/UID/GID/mode, without symlink traversal, and size-checked before reading. Verify signature against current database reporter authority; log fixed errors only. No report/payload logging or HTTP ingestion route.
- **New schema proposed:** one logged `remote_forward_reporters` row per cell, and one **UNLOGGED** `remote_forward_observations` row per venue/public route, bound to its current installation. The latter is an expendable latest observation, not durable history; crash/failover loss yields unknown. Current stores cannot represent authenticated gateway generation, route binding, report ordering and deletion without changing their existing meanings and retained history.
- `remote_forward_reporters`: `cell_id` PK/FK remote_cells ON DELETE CASCADE, `gateway_id` UUID, `generation` positive safe bigint, `public_key` Ed25519 SPKI text (max 256 chars), `minimum_manifest_sequence` positive safe bigint, `last_sequence` safe bigint default 0, `next_accept_at` timestamptz default negative infinity, `revoked_at` nullable timestamptz. `registerForwardReporter(client:PoolClient,input:{cellId:string,gatewayId:string,generation:number,publicKey:string}):Promise<void>` is trusted provisioning only: lock cell then reporter, require previous generation + 1 (first 1), a fresh key, set minimum manifest sequence to cell.sequence + 1 and reset cursor. `revokeForwardReporter(client:PoolClient,cellId:string,generation:number):Promise<void>` uses the same locks, requires the current generation and sets revoked_at; reactivation requires a new generation. No customer or new operator HTTP control.
- `remote_forward_observations`: `venue_id` PK/FK venues ON DELETE CASCADE, `installation_id` UNIQUE/FK installations ON DELETE CASCADE, `cell_id` FK remote_cells ON DELETE CASCADE, `gateway_id`, `generation`, `route_id` CHECK equals `public_availability`, `configuration_revision`, `route_binding` 64 lowercase hex, `manifest_sequence`, `manifest_expires_at`, `observation_sequence`, nullable checked `category`, `observed_at`, `received_at`, `expires_at`. Apply the protocol integer/range constraints and index `(cell_id,expires_at)`; never store envelopes or raw routing/error values in SQL.
- New `forward-observations.ts`: `ForwardObservationStore.constructor(pool:Pool,planMode:PlanMode='existing')`, `record(mapping:ForwardReportMapping,envelope:unknown):Promise<'accepted'|'ignored'>`, `readCurrent(client:PoolClient,installationId:string):Promise<PublicForwardView|null>`, `prune(cellId:string):Promise<number>`. Ingest locks organisation plan policies in UUID order, installations in UUID order, cell, reporter, then observations; recheck signature/current producer under those locks. Mutation paths already lock installations for configuration, hostname, movement, revocation and replacement (`packages/backups/src/replacement.ts`); preserve their policy-before-installation order and test real races. Reporter registration must never acquire installation locks after the cell lock.
- Accept only the mapped country/environment/cell, current active reporter, unrevoked/unsuperseded installation, exact venue/current placement cell/revision and recomputed route binding, with existing remote plan/setup eligibility. Require `minimum_manifest_sequence <= manifestSequence <= remote_cells.sequence`. Never accept staged-target, old-source-after-move or replaced-installation observations. A report signature authenticates the gateway's assertion of its applied manifest; it does not authenticate the venue application or prove an outside route works.
- Require report sequence above the persistent reporter cursor; observation sequences in `1..report.sequence` and strictly above the stored value for the same reporter stream. Reject duplicate installation/venue entries and mixed report/binding identities. Concurrent collectors serialize on reporter authority; update cursor and observations atomically, including ignored stale entries. A different current stream/binding replaces the venue's invalid old observation without comparing unrelated stream numbers. Replays cannot refresh expiry; SQL failure rolls back both, allowing an identical retry. A new generation invalidates old observations on every read, independent of cleanup.
- Proposed visibility TTL is **300,000 ms**: accept `observedAt <= databaseNow + 5,000 ms`, `observedAt < manifestExpiresAt <= observedAt + 600,000 ms`, and require `expiresAt = min(observedAt + 300,000, manifestExpiresAt)` with expiry after databaseNow. Also reject reports issued more than 300,000 ms ago or 5,000 ms into the future. A newer stream record cannot move observation time backwards. No replay or collection receipt extends these times.

Too-early snapshots are ignored until the next poll; then read the newest file. No arrival spawns work. Poll failures retry only next poll; a lost intermediate failure may never be shown. Owner copy says “last recorded attempt”, not a complete incident history.

Total cause storage is at most one row per venue; replacements, moves and revisions cannot add history. Keep the 64-route cell and current 64-address allocation cap (`placement.ts` provision/stageMove); revisiting address reuse requires revisiting this bound.

Add that argument to every dump in `scripts/schema-upgrade-receipt.mjs`; leave all other tables/evidence unchanged. Prove dump/restore exclusion in CI. P1/P3 deployment/backup integration must preserve that exclusion and primary-only reads before enabling reporting; no claim that their currently unbuilt adapters already do so.
