# Disposable test server implementation plan (D592)

> Execute approved slices inline. Before future implementation or test code, read `superpowers:test-driven-development`, write a failing behavioral test, observe the expected failure, implement minimally and observe it pass. This submission writes documentation only and stops for watcher review. No build before approval and server arrival.

**Goal:** Give Cloud local turns and ordinary CI jobs isolated disposable slots, reproduce the bridge on the permanent AX102, then assess Waitron separately.
**Architecture:** Off-server trusted-main admission, registrar and watchdog own generation-fenced leases; a narrow KVM manager creates one full VM/private Docker per turn or JIT job. Fail visibly and retry hosted explicitly.
**Stack:** Proposed KVM/QEMU on Debian 13, pinned Ubuntu guest matching CI, Node 26/pnpm 9.15.0 control/test tools, off-server GitHub Apps and durable conditional storage. Broker deployment/location needs approval.
**Spec:** [D592 design](../specs/2026-11-06-disposable-test-server-design.md), including inventory, source receipts and residual risk.

## Constraints and review focus

- Keep controller policy pinned to reviewed main. Candidates never execute in a privileged controller or on the host. No `pull_request_target`, server PAT, persistent service secret, host socket/mount or shared writable cache.
- One VM per job/local turn, destroyed once. Preserve existing selection, names, assertions, counts, concurrency and deadlines; coordinate with Lane H D591 without editing its work.
- Initial profile: 4 vCPUs/quota 4, 16 GiB RAM, disk cap 64 GiB; reserve >=4 physical cores with siblings, 16 GiB host RAM and 20% usable disk. These are proposed test limits, not actual capacity. Combine local+CI allocations and quarantines.
- Bounds: local admission 10s, CI creation-to-start 15min including boot <=120s and dispatch <=60s, local execution <=55min, heartbeat 15s/loss 60s, cleanup <=120s, cancellation request <=15s then normal grace 30s/terminal readback <=120s from detection. Pending cap 32. Preserve existing CI execution timeouts.
- Five review inputs need explicit tests below: duplicate/out-of-order events and stale reruns (2/5); malicious matching workflow (4); either watchdog process/host lost before any runner exists (5); full disk or uncertain cleanup beside a healthy neighbor (3); partial drain/second-host failure with pending work (7).
- This submission permits documentation commits and a docs-only PR. No provisioning, server access, spending or credential changes follow from it. Future approved code commits use `git commit -s` and active hooks. Never prune or delete resources you did not create.

Use a version-1 lease record with `repositoryId, workflowId, workflowPath, workflowDigest, head, tree, runId, attempt, jobId, jobName, policyDigest, hostGeneration, slot, generation, vmUuid, diskIds, networkIds, runnerId, imageDigest, createdAt, queueDeadline, executionDeadline, cleanupDeadline, state`. States are reserved, booting, ready, running, destroying, destroyed or quarantined; reserve/transition must compare the current generation. Resource IDs are generated by the trusted controller, never accepted as candidate paths.
